## 审查结论（2026-09-28）

本轮把三个开放项定下来，并修正了四处容易把假设写成事实的地方：

1. **A3：只做 3 个预设**：`default`（柔粉浅色，保留现有风格）、
   `dark`（夜间深色）、`sage`（护眼绿）。不另做一个和 `default` 重复的
   「浅色」预设；`default` 本身就是浅色预设。
2. **C4：选择工具条进入批量模式**。不采用长按（桌面端不可发现），也不让
   复选框常驻（列表默认态会变吵）。进入后提供「全选当前结果 / 完成 / 删除 /
   退出」，`Esc` 也能退出。
3. **A2c：本轮修复**。不仅修 `AiBubble.qml` 的用户消息气泡，也修共享的
   `PawButton.qml` 白字路径。后者之前被「只搜写死的 `#ffffff`」漏掉了，实际
   `primary` / `accent` / `danger` 三种按钮都可能用白字压在低对比度粉彩上。
4. **B1/B3：安全卡片不折叠，验收按状态分层**。`PermissionCard` 在左栏，
   还是高风险操作的常驻入口，不纳入普通信息卡折叠；AI 未配置时设置卡必须强制
   展开，不能为了追求一个总高度数字把用户的配置出口藏掉。

这些结论只改变开放项和实现细节，不推翻数据接缝、批量落盘、撤销语义、
验证协议等结构性决策。

### 「棘轮保护范围」和「本批迁移范围」是两件事

这两个概念原来混在一起（Codex 指出的），结果是**看数字的人不知道
哪个数字代表「我做完了」**。现在明确区分：

| | 是什么 | 数字涨了会怎样 | 没做完会怎样 |
|---|---|---|---|
| **棘轮保护范围** | 所有「不该涨的写死值」 | **红**，挡住提交 | — |
| **本批迁移范围** | 这一批实际要改的页面/属性 | — | **不算失败**，只是还没轮到 |

**棘轮该宽、迁移该窄。** 具体到当前：

```
棘轮保护范围（E1 第一批迁移**之后**的基线，共 272 处）
  ├── spacing   literal 106 + seam 59 = debt 165   ← 本批迁移只动这一块
  │             其中缩放轴接缝 1（历史遗留）
  ├── margin    literal  86 + seam  2 = debt  88（缩放轴接缝 2）
  └── padding   literal  19 + seam  0 = debt  19
```

（E1 第一批迁移**之前**的 `spacing` 是 `literal 164 + seam 1 = debt 165` ——
**debt 没变**，这正是「迁移 ≠ 还债」的体现：58 处只是从裸数字接到了密度轴上。）

**为什么保护范围要宽**：棘轮的作用是防止有人图快写回裸数字。
如果他改的是 `padding` 而棘轮不管 `padding`，那这个退步就溜过去了 ——
而「哪些属性算间距」和「这一批改哪些」本来就没有关系。

**为什么迁移范围要窄**：`margin` 有 88 处、`padding` 有 19 处，
把它们一起并进本批，会让这一批大到没法审。E2 只动 `spacing`，
因为密度轴对它的效果最直接。

> ⚠️ 别把这两个数字当成同一个进度条。**「棘轮绿了」不等于
> 「迁移做完了」** —— 棘轮绿只说明没人退步。同样，
> 「迁移没做完」也不会让棘轮变红。

### ⚠️ 一个会**假性归零**的棘轮比没有棘轮更糟

间距的值分**四类**，不是两类；棘轮盯**三个数**：

| 类 | 例子 | 含义 | 棘轮 |
|---|---|---|---|
| `literal` | `spacing: 10` | 裸数字，什么都没接 | **不能增加** |
| `seam` | `Theme.space(10)` / `Theme.px(10)` / `Theme.gap * 2` | 接了轴，**数值仍写死** | 与 literal 合计的 **debt 不能增加** |
| `token` | `Theme.gap` | 真的接了语义 token | 只许升 |
| `zero` / `indirect` | `spacing: 0` / `card.bodySpacing` | 见扫描器 docstring | 不计入债 |

**`seam` 这一类必须单独分出来**，否则会出现这种情况：

```
把 164 处 spacing: N 机械改成 spacing: Theme.space(N)
   → 棘轮的「写死数量」从 164 掉到 0
   → 看起来债还完了
   → 而 164 个数字一个都没少
```

> 这就是我原来那版扫描器的漏洞（判据是「值以 `Theme.` 开头就算 token」）。
> 现在判据是「**值里有没有字面数字**」：有 → `seam`，没有 → `token`。
> 误判方向刻意保守：宁可把已经接好的算成欠债，也不把还写死的算成完成。

**而 `seam` 自己还要再按「轴」分一层**（`scaleSeam`）——
因为 `Theme.space(N)` 和 `Theme.px(N)` **计数一样、行为不同**：

```
spacing: 8              恒为 8px（不跟 uiScale）
spacing: Theme.space(8) 恒为 8px（不跟）← 迁移到这里的正确形态
spacing: Theme.px(8)    6/8/10/16px（跟 uiScale 0.8/1.0/1.25/2.0）
```

迁错轴时 `literal −1 / seam +1 / debt 不变`，**只看总量的棘轮照样放行**。
实测过。所以 `scaleSeam`（接缩放轴的那部分）单独只许降。
详见 E1 那一节的推导。

> **总量防的是「欠债变多」，轴防的是「欠债接错地方」—— 两件事。**

## 二、阶段 A：主题预设

### A0【钉死】预设是**数据**，接缝在 `theme.resolved()`

三层叠加，顺序固定：

```
fixed_colors()           ← rose / roseSoft，永不进入预设或用户覆盖
      ↓
preset_colors(name)      ← 17 项完整表
      ↓
theme.json 的用户覆盖     ← 只覆盖这 17 项，优先级最高
```

`resolved(overrides, preset="default")` 是唯一的最终合成函数。**后端仍是唯一事实来源**
（`backend.themeColors` 的 docstring 已经这么写了）。

### A0.1【钉死】`theme.json` 的兼容格式

新格式如下，预设名和用户覆盖放在同一个文件，避免再增加一个设置键：

```json
{
  "preset": "default",
  "colors": {
    "accent": "#f4879f"
  }
}
```

读取必须兼容现有两种格式：旧的裸颜色映射，以及已有的
`{"colors": {...}}` 包装。读取旧格式时隐式使用 `default`；保存时统一写成
上面的新格式。未知预设名回退到 `default`，同时返回一条可展示的提示，不能
把界面留在半套颜色上。

建议的 Python 接口保持小而明确：

```text
load_config(path) -> {preset: str, colors: dict[str, str]}
save_config(path, preset, colors) -> (bool, message)
preset_colors(name) -> dict[str, str]       # 每次返回副本
resolved(overrides, preset="default") -> dict[str, str]
```

`Backend.themeColors` 继续只暴露 `resolved()` 的结果；另外提供只读的
`themePresets`（名称、中文名、说明）和当前 `themePreset`，设置页切换预设时
只改 `preset` 字段，不把颜色表复制进 `settings`。`resetTheme()` 的语义改为
「恢复当前预设」，另保留一个「恢复柔粉默认」入口，避免用户在深色主题里点
「恢复默认」却突然跳回浅色。

**为什么不把预设写进 QML。** QML 的 `pick(key, fallback)` 里那些字面量是
「backend 还没建好那一瞬间」的兜底，不是配置。把预设也放进去会得到**两份
事实来源**——而深色预设下 QML 兜底是浅色，一旦哪边漏了就是白屏闪烁。
这个项目在「同一个值存两份」上已经栽过三次（重复方式映射、套件清单、
版本常量），不要再来第四次。

### A1【钉死】可变角色必须等于 `pick()` 读的键集合

现状 19 ≠ 17，原因是 `ROLES` 把固定错误色也混在可变角色清单里。
不要只把两个元素从最终颜色表删掉；要把概念拆开：

```text
EDITABLE_ROLES = 17 个可改角色
FIXED_COLORS   = {rose, roseSoft}
PICK_KEYS      = 从 Theme.qml 的 pick("...") 实际解析出的 17 个键
```

不变量改成三条：

```text
keys(EDITABLE_ROLES) == PICK_KEYS
keys(preset_colors(name)) == PICK_KEYS
keys(resolved(...)) == PICK_KEYS ∪ keys(FIXED_COLORS)
```

`rose` / `roseSoft` 仍由 QML 固定写出，也仍由 `resolved()` 返回给需要完整
色表的后端调用者，但它们不出现在 `themeRoles`、预设表或用户覆盖中。

理由：`Theme.qml:60` 的注释已经写明了这是刻意的设计——

> `rose / roseSoft 刻意不开放：错误色如果被改成和背景相近，用户就看不到失败了。`

这是安全决策，尊重它。反过来的做法（开放它）等于让用户能把「失败」调成看不见。

测试必须从 `Theme.qml` 的真实 `pick("...")` 文本解析键集合，不能在测试里
再手写一份 17 键常量；否则把 QML 的 `pick("accent")` 改成拼错时，测试
仍可能拿自己的常量互相比较而全绿。

### A2【钉死】预设必须**完备**，靠测试保证，不靠运行时兜底

每个预设必须给出**全部** 17 项。缺项在运行时不会报错——`pick()` 会退回
QML 里的浅色字面量，表现出来只是「深色模式下某块是白的」，很难发现。

纯数据测试（不需要起界面）：

```
对每个预设：
  · 键集合 == EDITABLE_ROLES / PICK_KEYS（缺一个就红）
  · 每个值通过 is_valid_color()（格式）
```

### A2b【钉死】对比度门槛用**棘轮**，不用绝对值

**这一条我改过两次，两次都是因为先写结论再验证。**

第一版写的是「正文 ≥ 4.5:1、次要 ≥ 3:1」，但算了一遍发现
**默认主题自己过不了**（下面有表）—— 拿一个产品当前达不到的标准去要求
新预设，是在挖坑：要么 Codex 违反规则，要么被迫改默认配色，
而那不是他的任务。

第二版我把「白字 on accent/violet/mint/gold」四行都列成不达标。
**这次复核发现原结论漏搜了共享组件**：字面量搜索确实只看到气泡文字和
开关圆点，但 `PawButton.qml` 的 `_fg` 是运行时返回 `#ffffff`，实际覆盖
`primary` / `accent` / `danger` 三种按钮。因此这是已核实的交互文字问题，
不能继续按「只有气泡一处」处理。

修复前的当前默认主题基线（WCAG 对比度，公式算的）：

| 配对 | 实测 | AA | 说明 |
|---|---|---|---|
| `text` on 四种底色 | 8.82 ~ 10.49:1 | 4.5 | 达标 |
| `textDim` on 四种底色 | 4.41 ~ 5.25:1 | 3.0 | 达标 |
| `textFaint` on `bg`/`surface`/`surfaceAlt` | 3.13 ~ 3.44:1 | 3.0 | 达标 |
| `textFaint` on `surfaceHi` | **2.89:1** | 3.0 | 差一点 |
| 白字 on `violet`（用户消息气泡） | **2.74:1** | 4.5 | 见 A2c |
| `PawButton` 白字 on `accent` / `violet` / `rose` | **2.38 / 2.74 / 3.29:1** | 4.5 | 见 A2c |

门槛这样定：

```
文字类（text / textDim / textFaint on 四种底色）：
    ≥ 3.0:1，且不低于修正后 default 预设的同项
用户消息气泡（readableOn(violet)）和填充按钮文字：
    ≥ 4.5:1
其余任何「前景画在背景上」的配对：
    不低于修正后 default 预设的同项（棘轮，不倒退）
```

即：**新预设不许比修正后的现状更差**，文字类另加绝对下限 3.0，
交互文字单独守 4.5。这样既保留粉彩审美，也不会把可读性债务复制到深色主题。

颜色前景不能在每个调用点凭感觉选。新增 `Theme.readableOn(color)`，在白色
和固定深色 `#211a25` 之间选择对比度更高者，至少用于：

```text
PawButton.qml：primary / accent / danger 的文字与 glyph
AiBubble.qml：用户消息气泡文字
```

这样浅色粉彩、深色主题和用户自定义 accent 都走同一条规则，不再把「白字」
写死在共享按钮里。测试读 QML 运行后的真实 `Text.color`，不能只断言源码
里出现了 `readableOn`。

**对比度用公式算，不靠肉眼。** 公式见附录。

### A2c【开放·本次决定：修复】用户消息与填充按钮的文字对比度

`AiBubble.qml:90` —— 用户自己发的那条消息是**白字画在 `Theme.violet`
（#b48ae0）气泡上**，对比度 **2.74:1**（AA 要求 4.5）。

这是现在就有、和加预设无关的可读性问题。有一点讽刺：**用户自己的话
比小爪的回复更难读**（助手气泡是深色 `text` on 浅底，9~10:1）。复核时
还发现 `PawButton.qml` 的共享 `_fg` 对三种填充按钮都固定返回白色，
默认主题的 `accent` / `violet` / `rose` 分别只有 **2.38 / 2.74 / 3.29:1**。

根因：`violet` 是粉彩（pastel）色，粉彩和白色天生对比度低。
标准解法是在粉彩上用**深色**文字，而不是把背景色硬改成刺眼的深色。

**本轮顺手修复，但不改用户气泡的尺寸链路**：

- `AiBubble.qml` 只把用户文字颜色改为 `Theme.readableOn(Theme.violet)`；
  不改宽度、内边距、高度或 `TextMetrics`，避免重新触发那段布局注释记录的
  四个坑。
- `PawButton.qml` 的三个填充变体统一改用
  `Theme.readableOn(control._bg)`；ghost 按钮仍使用 `Theme.textDim`。
- `PawSwitch.qml` 的白色滑块圆点和 `FocusPage.qml` 的进度头是图形元素，
  不把它们误算成文字对比度问题。

| 填充按钮文字最低值 | 5.15:1 | 5.15:1 | 4.65:1 |

否则用户把 accent 改成浅黄色后问题会重新出现。

**另外记一条给以后：** `AiBubble.qml` 里那段注释（第 99~108 行）记着
这个气泡踩过的四个布局坑（高度与宽度互锁成环、连续换内容时高度不刷新
…）。**改它的任何尺寸都要先读那段注释。**

### A4【钉死】用户改过颜色之后切换预设的行为

三种可能，我定第一种：

1. **预设是底，用户覆盖在其上**。切预设时保留 `theme.json` 中的 `colors`
   （用户的覆盖继续生效）。设置页明确显示「已基于【深色】自定义 N 项」+
   一个「恢复此预设」按钮。
2. 切预设时清空用户覆盖。（简单，但用户调了半天的颜色突然没了）
3. 每个预设各存一份覆盖。（复杂度爆炸，45+17×N 个键）

选 1 的理由：现在 `theme.describe()` 已经在做「只说真的和默认不一样的项」，
只需把比较基准改成当前 `preset_colors(preset)`；用户知道自己在预设之上改了
什么，也能一键退回去。接口改为 `describe(overrides, preset="default")`，
不能继续拿柔粉默认值比较深色预设，否则切到深色后会把整张表误报成「用户改过」。

「恢复此预设」只清空 `colors`、保留当前 `preset`；「恢复柔粉默认」才同时把
`preset` 设为 `default`。两者都必须先写临时文件、替换成功后再发
`themeChanged`，保存失败时界面和摘要都不应假装已经切换。

## 三、阶段 B：AI 页折叠

### B1【钉死】用共享组件，不用每面板各写一份展开状态

新增 `CollapsibleSection.qml`，注册进 `qmldir`（和 `Card` 同级）。

理由：右栏的三个信息面板（`AiSettingsPanel` / `AiMcpPanel` /
`AiHistoryPanel`）现在是独立组件，但**普通信息折叠是同一件事**。共享组件
统一动画时长、箭头方向、标题点击区和键盘可达性，避免三处各自漂移。

`PermissionCard` 不包进这个组件：它在左栏，是权限/高风险操作的安全入口，
无待确认时仍显示当前级别，有待确认时必须保持完整可操作，不能靠折叠把风险
提示和确认按钮藏起来。

#### 先说清楚：已有的两套「折叠」和这个不是一回事

代码里已经有类似机制，我核实过它们的语义，**别把它们当成同一个东西合并**：

| 现有机制 | 位置 | 实际语义 |
|---|---|---|
| `page.showHistory` → `AiHistoryPanel.expanded` | `AiPage.qml:21,354` | **整张卡片显示/隐藏**，由页面上的按钮切换（第 328~330 行） |
| `page.showMcpDetail` → `AiMcpPanel.showDetail` | `AiPage.qml:27,457` | 卡片内**详细区**的开关 |

本方案要的是第三种（仅用于右栏普通信息面板）：

```
CollapsibleSection：卡片**始终可见**，默认只显示标题栏，
                    点标题（或箭头）展开正文
```

三者的区别是实质性的：前两种是「这块内容要不要出现」，
第三种是「这块内容以什么形态出现」。**统一它们属于范围外**，
真要动的话单独提。

`AiHistoryPanel` 的 `expanded` 属性名和第三种语义撞了，
实现时注意别混（必要时改名，但那是它自己的事）。

共享组件的最小接口固定为：

```text
title / subtitle
expanded / expandedChanged
defaultExpanded
contentItem（正文槽）
```

标题栏必须是一个完整的可聚焦按钮区域，鼠标点标题和箭头都能切换；
`Space` / `Enter` 切换，`Esc` 只退出当前折叠焦点，不触发删除或权限动作。
动画只改变正文高度和 opacity，不用 `visible: false` 造成键盘焦点落到隐藏项。

### B2【钉死】v1 **不新增 settings 键**，展开状态只在会话内记忆

理由：`settings` 已经 45 个键，而展开状态是**可重新推导的廉价状态**。
加进去会：让设置项继续膨胀、让「恢复默认」要处理它、
让导入导出多一份要迁移的数据。

会话内记忆（页面级属性）就够了：切页回来还是展开的，重启回到默认。

**本次决定：按配置状态给默认值，而不是死写「第一个」。**

```text
AI 已配置、没有待确认动作：
  历史 / 模型设置 / MCP 详情默认收起；聊天区保持展开。
AI 未配置：
  模型设置强制展开，历史和 MCP 详情收起。
出现待确认问题或权限动作：
  对应卡片强制展开并滚动到可操作位置，不能被默认折叠覆盖。
```

用户在本次打开页面后的展开/收起选择只保存在 `AiPage` 的页面属性里；
切页回来保留，重启回到上面的默认值。未配置状态的强制展开优先级最高，
避免新用户只看到一个空聊天框却找不到 API Key 入口。

### B3【钉死】折叠的收益必须量化断言

这是我测出来的数字，可以直接当验收标准；但必须区分配置状态：

```
工作台 860×560 → AI 页 Flickable：
  改动前 contentHeight = 2025px（6.1 屏）
  已配置 + 无待确认动作 + 默认折叠：contentHeight < 900px
  未配置：模型设置强制展开，单独验收设置卡可见且可操作，
          不用 < 900px 这条把配置入口压没
  有待确认动作：对应卡片可见、按钮可点击，且滚动后不被输入区遮挡
```

**不是「看起来好点了」，是能红的数字和可操作性断言。** `aipreview.py`
必须分别构造「已配置 / 未配置 / 有待确认」三种后端状态；不能只截一个
恰好把设置卡隐藏掉的快照。

## 四、阶段 C：待办批量编辑

### C1【钉死】选择态在**视图层**，不在模型层

「哪些被勾选了」是 QML 属性，不是 `TaskModel` 的字段。

理由：`TaskModel` 同时被 AI 工具驱动（`ai/tools.py` 里有待办工具）。
选择态一旦进模型，一次 AI 调用就可能改变用户正在勾选的东西——
用户勾了 5 条准备删，AI 顺手加了一条待办触发了 `_rebuild`，
勾选状态错位，**用户删掉的不是他想删的**。

### C2【钉死】批量操作是一次落盘，不是 N 次

新模型槽收 `list[str]`（id 列表），内部**只调一次 `_touch()`**。

一次 `_touch()` = 一次 `store.save()` + 一次模型重置 + 一次信号。
删 20 条如果走 20 次单条接口，就是 20 次全量写盘（对话历史那条经验：
全量重写是 O(文件大小)）。

接口只接收 ID，不接收 QML 行号；进入模型后先做去重、空值过滤和
「仍存在于 `store.tasks`」校验。批量完成与批量删除都要在内存中完成整批
变更，最后只调用一次 `_touch()`。批量完成要按「原来未完成」的条数更新
`stats[today].tasks_done`，不能循环调用 `toggle()`，否则既会重复保存，也会
把排序/信号触发 N 次。

### C3【钉死】撤销语义扩展为「**最后一次操作**」，批量的整体撤销

现在 `_last_removed` 只存一条。批量删除之后，用户按「撤销」期望的是
**恢复刚才删掉的那一批**，不是恢复其中一条。

所以语义统一成「撤销上一次操作」：

```
_last_removed: 单条删除 → 一个元素
               批量删除 → N 个元素
               撤销     → 一次性全部恢复
```

批量记录保存每个任务的完整副本和原始索引；撤销时按原索引升序恢复，保证
被删任务之间的相对顺序不变。撤销条显示「已删除 N 条」，单条时仍显示任务名。
若删除后用户又新增/排序，绝对索引允许因列表变化而偏移，但不能恢复重复 ID，
也不能只恢复其中一条。

**不做多级撤销栈。** 用户真正会用的就是「我刚才删错了」这一种；
栈会带来「撤销到第几步了」的界面负担。这个取舍之前已经定过一次
（单个模型时），批量沿用同一个。

### C4【开放·本次决定】工具条进入选择模式

采用「列表工具条 → 选择模式」，不采用另外两种：

| 方案 | 决定 | 原因 |
|---|---|---|
| 复选框常驻 | 不选 | 默认态每行多一个强视觉元素，列表密度下降；用户只是浏览时没有收益 |
| 长按进入 | 不选 | 桌面端没有长按提示，鼠标和键盘用户很难发现；也和双击编辑冲突 |
| 工具条进入 | **选用** | 入口可见、点击目标稳定，批量状态和单条编辑状态分离 |

在当前筛选/搜索行右侧增加「选择」按钮。进入后：

```text
顶部工具条：已选 N 条 · 全选当前结果 · 完成 · 删除 · 退出
每行左侧：仅在选择模式显示复选框；点击行/复选框切换该 ID
键盘：Ctrl+A 选中当前结果，Esc 退出，Delete 等同「删除」并先确认
```

交互不变量：

- 「全选当前结果」只作用于当前筛选和搜索后的可见 ID，不悄悄操作被过滤的任务；
  已全选时按钮变为「取消全选」。
- 「完成」只把选中且未完成的任务标为完成；完成项不重复计数，操作后清空选择
  并退出选择模式。
- 「删除」必须弹出带数量的确认框；确认后整批删除并显示可撤销条，取消不改变
  选择和数据。
- 退出路径至少有工具条「退出」、`Esc`、完成/删除后的自动退出；点击筛选、
  搜索或模型重建时清理不存在的 ID，不能把选择态卡死。
- 选择集合按任务 ID 保存，不按 delegate 行号保存；AI 新增任务或模型重排不能
  改变已经选中的任务。

**已知约束**：`TasksPage.qml` 现在**没有任何多选代码**（`selected` /
`multiSelect` / `checkedIds` 全是 0 处命中），所以是从零加，不是改。

## 五、阶段 D：设置分层

### D1【钉死】`advanced_mode` 的准入用**规则**，不用逐个拍脑袋

现在只门控 2 处。扩展时必须有可复述的判据，否则会变成「谁顺手谁加」。
注意：`default_settings()` 的 45 个键里包含迁移标记和运行参数，不能把
「有键」误算成「设置页必须有一个控件」。

规则：

> 一个设置项进 `advanced_mode`，当且仅当它**同时**满足：
> 1. 泛用户不需要改（默认值对大多数人是合适的）
> 2. **改错的代价 > 用不上的代价**
>
> 典型的第 2 条：需要外部前置条件（API Key、MCP 服务器、知识库文件），
> 或者改了之后在界面上看不出效果。

这条规则只判断「功能设置」；`advanced_mode` 是分层本身的控制，不参与归类，
必须常驻。迁移标记和运行时缓存也不属于设置项，不渲染控件。

反例（**不该**进门控）：`pet_scale`、`notify_enabled`、主题预设——
泛用户会想改，而且改错了当场看得见。

### D2【开放·本次决定】按规则给 45 个设置项分类

先说明边界：主题预设/颜色继续放在 `theme.json`，不是 `settings` 的 45 个键。
45 个键按下面四类处理；「内部」不是删掉，而是继续由迁移/运行逻辑维护，
不在设置页渲染控件。`advanced_mode` 本身是唯一例外：它是分层开关，
必须始终可见，不能把用户锁在高级设置之外。

```text
基础（23，默认可见）
focus_minutes, short_break_minutes, long_break_minutes,
rounds_before_long_break, auto_start_next, sound_enabled, notify_enabled,
pet_scale, pet_opacity, ui_scale, always_on_top, fade_when_idle, autostart,
sit_reminder_minutes, sit_reminder_enabled, afk_minutes, daily_goal_minutes,
quiet_when_fullscreen, ai_level, pet_click_action, pet_style,
pet_snap_enabled, update_check

高级（14，advanced_mode 开启后可见）
hotkey_dashboard, hotkey_focus, hotkey_task, hotkey_ask,
command_bar_anchor, pet_snap_distance, pet_edge_pose,
ai_max_steps, ai_memory_enabled, ai_auto_screenshot, ai_show_cursor,
ai_mcp_enabled, ai_openai_model, ai_openai_base

分层控制（1，始终可见）
advanced_mode

内部（7，不渲染设置控件）
move_step, clock_format, pet_snap_hide_ratio, onboarding_done,
update_last_check, update_last_check_ok, update_skipped_version
```

分类理由：四个全局热键和指令栏位置需要用户理解快捷键语法，写错后通常要
重启才能发现；贴边距离/姿势是调好即忘的细节；AI 步数、记忆、截图、MCP 和
服务商参数要有外部前置条件，改错的代价高于暂时看不到它们。相反，缩放、
宠物大小、通知、专注时长和 AI 权限是第一次使用就可能要调的，留在基础层。

实现上不要把整个模型配置卡藏进高级模式：未配置 AI 时，API Key 入口仍然
必须可见。自定义十六进制颜色也放到「主题预设」下的高级编辑区，但预设选择
和恢复当前预设按钮保持基础可见。

### D3【钉死】分层要有量化验收

```
测量条件：908×590 设置页、advanced_mode = false、未展开颜色编辑、
无更新可用、默认数据副本。
改动前实际可见控件：29 个
  PawSwitch 7 + PawSlider 4 + PawField 4 + PawButton 14
最低验收：改动后 ≤ 21 个（相对下降 ≥ 25%）
目标值：≤ 20 个；若低于目标，不能通过移除基础入口来换数字。
```

理由同 B3：没有视觉回归设施，只能靠数字。而且这个数字能防止
「加了门控但其实只藏了一个开关」这种自我安慰式的改动。

测试必须实际加载 `SettingsPage.qml`，按 `QQuickItem.isVisible()` 统计四类
控件；不能用 grep 统计 `visible:` 行，也不能把父卡片隐藏但子控件仍占位的
情况误判为通过。另加反向断言：基础入口（缩放、主题预设、宠物大小、通知、
AI 未配置时的模型设置）仍有可见、可交互控件。

## 六、阶段 E：紧凑模式 —— **暂缓，不是不能做**

### E0【修正】先说清这一段的结论到底是什么

**这一节我改过一次标题和结论。**（原稿写的是「本轮不做」，读起来像
「这件事做不了」，那是错的。）

准确的表述是：

> **E 阶段不是「无法修改」，而是「不能安全地一次性修改」。**

区别是实质性的：

| 说法 | 含义 | 对不对 |
|---|---|---|
| 「紧凑模式做不了」 | 永远不做 | ❌ 错。技术上完全可行 |
| 「本轮不做」 | 含糊 —— 是搁置还是放弃？ | ⚠️ 表述不清，容易被读成前者 |
| **「不能安全地一次性做」** | **需要先还基础设施的债，分步做** | ✅ 准确 |

所以这一阶段的定位是**下一阶段的基础设施工作**，不是「排除项」。
配套的三步路径见 E2。

### E1【钉死】为什么不能一次性做 —— 四条理由，都有数字

#### 理由一：`ui_scale` 耦合了字号和间距，不能复用

`Theme.px(v) = round(v * scale)`，而 `scale` 来自 `backend.uiScale` ——
**间距和字号共用同一个系数**。它是「整体缩放」（给看不清的人用的），
不是「紧凑」（给想一屏看更多的人用的）。

紧凑要的是**间距降、字号不变**，所以必须是独立轴，不能借 `ui_scale`。

#### 理由二：间距的 token 化率比看上去更差

**数字来自 `tools/spacingtest.py`**（唯一扫描器，口径见它的 docstring）：

| 类别 | token | 写死 | 零值 | 间接 | 合计 | token 率 |
|---|---|---|---|---|---|---|
| **`spacing`** | 11 | **164** | 5 | 2 | 182 | **6.0%** |
| `margin` | 56 | **86** | 0 | 1 | 143 | 39.2% |
| `padding` | 0 | **19** | 3 | 1 | 23 | **0.0%** |
| **合计** | **67** | **269** | 8 | 4 | 348 | **19.3%** |

**这张表的三个用处：**

- `margin` 类已经有 **39.2%** 走 token（其中 `Layout.*Margin` 那块基本做完）
  —— 有人做过一轮，别重复劳动
- **`spacing` 才是真正的大头：164 处写死，只有 11 处走 token**
- **`padding` 是这次才发现的债**：19 处写死、**0 处走 token**，
  之前的扫描根本没把它算进「间距」

现在加一个 `density`，只有 **6.0%** 的 `spacing` 会跟着变 ——
结果就是**「有的地方紧、有的地方不紧」**，比不做更糟。

> **口径的两个细节**（都是被质疑后补上的，不是随手定的）：
>
> 1. **零值（8 处）单列，不计入债**：`spacing: 0` / `padding: 0`
>    表示「元素紧贴」，而 `0 × 密度 = 0` —— 紧凑模式下它本来就不变。
>    算进债里会让棘轮永远归不了零，还会诱导出没有意义的改动
>    （`spacing: 0` → `spacing: Theme.zero`）。
> 2. **间接引用（4 处）单列**：值是 `card.bodySpacing` 这类表达式。
>    实测那 2 处指向 `Card.bodySpacing: 10` —— 说明**要彻底 token 化，
>    得连 `Card` 的属性默认值一起改**，不是替换一处就完事。
> 迁移的标的是 `spacing` 和 `anchors.margins`，不是 `Layout.*Margin`。

#### 理由三：尺寸是**推导**出来的，改间距会链式重算

| 指标 | 数量 |
|---|---|
| `Layout` 容器（Column/Row/Grid/Stack） | 175 |
| `implicitHeight` | **104** |
| 固定 `height: <数字>` | 36 |

**`implicitHeight` 比手写 `spacing` 的一半还多**，说明大部分尺寸是
**内容自撑**推导出来的。推导链越长，局部改间距越容易在某处塌掉 ——
表现就是按钮挤压、文本换行、滚动区域异常。

这 104 处不是「迁移成本」，是**风险来源**：它们不需要改，
但会在间距变化时重新计算，而**没有任何测试盯着算得对不对**。

#### 理由四：59/59 的逻辑回归保证不了视觉

回归是逻辑测试（数据、行为、断言）。它抓得住「函数返回错了」，
抓不住「这个卡片现在挤成一团」。

**没有视觉回归设施**，所以紧凑模式的正确性无法自动验证 ——
这决定了它必须**小步做**，每步都能人工看。

### E2【钉死】三步路径（这一步是 Codex 提的，比原稿好）

原稿把 E 当成一件事，只给了「先 token 化」再「加全局开关」两步。
**Codex 在中间插了一步「局部紧凑」，这个补充是对的**，采纳：

```
E1  间距 token 化（纯基础设施，不动视觉）
      ↓
E2  局部紧凑：只支持 AI 页 + 待办页
      ↓
E3  全局开关：comfortable / compact
```

**为什么 E2 这一步是必要的（而不是直接从 E1 跳到 E3）：**

- **缩小承诺范围**。只做两个页面，就不必承诺「全工作台都紧凑」——
  那是个大得多的承诺，而且每多一个页面就多一处可能塌掉的推导链。
- **提前拿到真实反馈**。AI 页信息密度提升最明显（实测 2025px 塞在
  330px 视口里），待办页次之。这两个页面验证过了，才知道 `density`
  的取值合不合适。
- **失败可退**。局部紧凑出问题只影响两个页面，不用回滚整个功能。

**E1 的验收：棘轮测试**（已实现为 `tools/spacingtest.py`）

```
断言：literal 不增加
      debt（literal + seam）不增加        ← 允许 literal → seam 的接缝迁移
      scaleSeam（接缩放轴的那部分 seam）不增加   ← 防「接错轴」
```

目标：允许 `literal → seam` 的接缝迁移，但不允许回退、伪完成、**或接错轴**。

基线写在 `spacingtest.py` 的 `RATCHET` 里。E1 第一批迁移前的实际值是
`spacing literal=164 / debt=165`、`margin literal=86 / debt=88`、
`padding literal=19 / debt=19`；当前基线已更新为本批迁移后的
`spacing literal=106 / debt=165 / scaleSeam=1`，其余两类不变。

#### 为什么棘轮要盯三个数，而不是两个

**`debt` 而不是「`seam` 自己只许降」。** 把裸数字迁成 `Theme.space(N)`
是 E1 的**预期动作**：`literal` 减 1、`seam` 加 1。如果要求 `seam` 只许降，
第一批 58 处迁移就会被自己的棘轮拦住，唯一的出路是把 `seam` 基线往上改
—— 而那正是工具报错文案禁止的（「棘轮不是用来记录现状的」）。
**那条规则是自相矛盾的，不是「不方便」。**（这是 Codex 发现的，我复核
并做了状态转移矩阵：旧规则确实拦住合法迁移，同时它「拦住」接错轴也只是
误伤 —— 拦的是「seam 涨了」这个症状，不是病灶。）

**`scaleSeam` 是补的一个真洞。** `seam` 里混着两种**不同轴**的写法：

| 写法 | 接的轴 | 跟 uiScale 吗 | 裸数字迁到这里对吗 |
|---|---|---|---|
| `Theme.space(N)` | 密度 | **不跟** | ✓ 对 |
| `Theme.px(N)` | 缩放 | **跟** | ✗ 错 |
| `Theme.scaledSpace(N)` | 缩放 × 密度 | **跟** | ✗ 错 |

裸 `spacing: 8` 恒为 8；迁成 `Theme.px(8)` 之后 uiScale=2.0 时变 **16**
（实测：`space(8)` 在 0.8/1.0/1.25/2.0 下都是 8，`px(8)` 是 6/8/10/16）。
**而计数上两者完全一样**（`literal −1`、`seam +1`、`debt` 不变）。

实测确认：把一处 `spacing: Theme.space(8)` 换成 `Theme.px(8)`，
`literal` 和 `debt` 都持平、**棘轮通过**。加上 `scaleSeam` 之后同一个注入
报 `[XX] 1 → 2 涨了`，退出码 1。

> 只盯总量会让「接错轴」和「接对轴」看起来一模一样。
> **总量防的是「欠债变多」，轴防的是「欠债接错地方」—— 两件事。**

**棘轮做过 V2 注入验证**：

- 把一个 `spacing: Theme.space(8)` 改回裸数字，`literal 106 → 107`，退出码 1；
- 把一个纯 token 改成 `Theme.space(12)`，`debt 165 → 166`，退出码 1；
- 把一个 `spacing: Theme.space(8)` 改成 `Theme.px(8)`，`scaleSeam 1 → 2`，
  退出码 1（加轴之前**这一条是放行的**）。

三次都已还原（逐字节核对）。**所以它是真的会响，不是摆着好看的。**

棘轮而不是一次性全改的理由：269 处写死的间距分散在约 20 个文件，
一次性改的风险是布局悄悄坏掉，而**我们没有视觉回归设施**能抓住它。
棘轮让这笔债可以分批还，且不会倒退。

**E1 迁移的优先级**（按实测数量排，不是按主观感受）：

| 文件 | 手写 spacing | 固定高度 | 备注 |
|---|---|---|---|
| `page/SettingsPage.qml` | 23 | 4 | |
| `page/AiPage.qml` | 25 | 0 | E2 的目标页面 |
| `AiSettingsPanel.qml` | 21 | 0 | E2 的目标页面 |
| `page/RemindersPage.qml` | 17 | 1 | |
| `page/TasksPage.qml` | 12 | 1 | E2 的目标页面 |
| `Dashboard.qml` | 7 | 10 | 固定高度最多 |

**先迁 E2 要用的那三个页面**（`AiPage` / `AiSettingsPanel` /
`TasksPage`），这样 E1 做完就能直接接 E2，不用等全部迁完。

**E1 第一批已完成（2026-09-29）**：上述三个文件共迁移 58 处裸
`spacing` 到 `Theme.space(N)`。`density=1` 下默认视觉保持不变；当前扫描器
结果为 `spacing literal=106 / seam=59 / debt=165`。这一步只是把密度轴接入
页面，`seam` 仍算未完成债务，不等于已经完成语义 token 化，也没有公开 compact
开关。

### E2 的实测结果（2026-09-30 → 10-01，`tools/densitytest.py`）

> ✅ **E2 已完成（2026-10-04，Codex 独立复核通过）。**
> 复核结论：`densitytest 31/31`、`spacetest 47/47`、`spacingtest` 基线保持、
> 截图人工比对无异常。**E2 收束于此，不继续扩到 `SettingsPage`** ——
> 理由见下面的「为什么停在这里」。

#### 第一轮（只有 E1 的迁移，**待办页无效**）

| 页面 | `density=1.00` | `0.90` | `0.85` | `0.70` | 变化 |
|---|---|---|---|---|---|
| AI 页（含模型设置面板） | 2167px | 2071 | 2071 | 2008 | **−7.3%** |
| 待办页 | 338px | 338 | 338 | 338 | **0.0%** |

**两个结论和预期不一样，都很重要：**

#### 一、待办页在 `density=0.70` 时**一点都没变**

原因精确，不是「效果不明显」：

```qml
// TasksPage.qml:344
delegate: Rectangle {
    implicitHeight: rowColumn.implicitHeight + 16     // ← 裸字面量 16
```

任务行高 = 列内容高 + **16px 裸字面量**。而那个列里唯一的纵向
`spacing` 是 `Theme.space(2)` —— **`2 <= 4`，被小值门槛保护**，
不参与密度缩放。

所以「任务行内边距不缩」有**两个**独立原因：那个 `16` 是表达式里的
裸数字（扫描器不算它是间距），而那个 `2` 被门槛挡住了。
**这个页面要想真变紧，两处都得动，而两处都不在 E1 的射程里。**

#### 二、`density` 档位里有**成对的重复**

用迁移过的真实值集合算（JS 的 `Math.round`）：

```
   value   1.00   0.95   0.90   0.85   0.80   0.75   0.70
       6      6      6      5      5      5      5      4
       7      7      7      6      6      6      5      5
       8      8      8      7      7      6      6      6
      10     10     10      9      9      8      8      7

档位重复：[1.0, 0.95] 完全相同    [0.9, 0.85] 完全相同
```

**七个档位实际只有五个效果。** 因为迁移过的值集中在 `{6,7,8,10}`，
它们在 0.90 和 0.85 下四舍五入到同一组整数
（`8×0.90=7.20→7`、`8×0.85=6.80→7`）。

这直接回答 E4 的开放问题：**档位不能按 0.05 均匀取**，否则有两个是白给的。
（也解释了实测里 0.90 和 0.85 的内容高度一模一样。）

#### 三、文本裁切：没有**新增**，但有 3 处**既有**的

`densitytest.py` 的判据是「相对 `density=1.0` 基线没有**新增**裁切」，
因为 `AiSettingsPanel.qml` 里三个 `QQuickText` 在 E2 之前就是
`height < contentHeight`（14/16 而内容要 19）。

**但这 3 条不能当成视觉缺陷清单。** `height < contentHeight` **不等于**
「文字被切」—— 只有祖先 `clip: true` 或自身设了 `elide`，超出的字形
才真的看不见；否则只是**盒子比理想高度矮**，字形照常渲染。

而且我**只确认了其中 1 处的视觉表现**（输入框占位文字
`先在上面配置模型 API Key` 在截图里字形完整），另外两处
（`PawSwitch` 的标签）没有逐个确认过。所以：

> 这条断言的价值在**相对比较** —— 「新增了」说明有东西变了；
> **不能把它的输出当成「这些文字有问题」的结论。**

（这一点我自己先写成了「这 3 处肉眼看不出来」，是**超出证据的声明**，
改回来了：只报我验过的。）

#### 四、一个我自己看走眼的地方（记下来）

看截图时我以为 `density=0.70` 下有个按钮被压扁了 —— 同一块屏幕区域里
它只露出一条。量下来：

```
density=1.00  按钮 x=0 y=4 w=200 h=34 implicitH=34
density=0.70  按钮 x=0 y=4 w=200 h=34 implicitH=34   ← 完全一样
唯一的 clip 祖先是 rightScroll（滚动视口，h=450 / 464）
```

**不是被压扁，是内容整体上移后滚动视口正好切到它** —— 正常滚动行为。

> **固定屏幕区域跨 density 比像素是误导的** —— 内容会整体上移，
> 同一个屏幕位置在不同 density 下对应的是**不同的元素**。
> 截图层适合判断「看起来对不对」，不适合判断「有没有坏」。

#### 第二轮（2026-10-01，接入待办页的行内留白之后）

Codex 第 6 轮决定：把 `TasksPage.qml:347` 的裸 `+ 16` 接上密度轴，
档位去掉重复的 `0.85`。改完实测：

| 页面 | `density=1.00` | `0.90` | `0.80` | `0.70` | 变化 |
|---|---|---|---|---|---|
| AI 页 | 2167px | 2071 | 2027 | 2008 | **−7.3%** |
| 待办页 | 338px | 326 | 320 | **308** | **−8.9%** |

**四档现在互不相同**（AI：2167/2071/2027/2008，待办：338/326/320/308），
而 `density=1.00` 的待办页仍是 **338px** —— 证明
`+ Theme.space(16)` 在默认档**逐像素等于原来的 `+ 16`**。

##### ⚠️ 这个 `Theme.space(16)` 是 **E2 新增的接缝，不属于 E1 的 58 处迁移**

```qml
implicitHeight: rowColumn.implicitHeight + Theme.space(16)   // E2 新增
```

它是**表达式里的数字**，不是 `spacing:` 属性的值 ——
**E1 的扫描器看不到它**（`implicitHeight` 不在 `SPACING_PROPS` 里，
实测扫到 0 处）。所以：

  · E1 的扫描基线**不变**（仍是 `spacing literal=106 / debt=165 /
    scaleSeam=1`）
  · 但待办页在 E1 做完时**仍然纹丝不动**，因为挡住它的是这个
    扫描器看不见的数字 —— **「棘轮绿了」和「页面真的变紧了」是两件事**，
    这里正好是一个实例

**为什么当时没有写进 E1 口径**：那会引出「表达式里的裸数字算不算间距」
这个**口径变更**，按约定要双方同意。Codex 第 6 轮明确它是 E2 的局部
视觉实现、不回写 E1 基线。

##### 新断言是「严格变矮」，不是「不增」

原来对内容高度写的是**单调不增**（`vals == sorted(vals)`）——
而待办页在接缝之前是 `338 → 338`，**完全相等也照样通过**。
这正是「恒真断言」的来源（我自己犯过一次，见下面第五节）。

现在加了一条**严格变矮**：从最大 density 到最小 density 必须
`bottom < top`。**注入验证**过：

| 注入 | 结果 |
|---|---|
| 接缝改回裸 `16`（= E2 之前） | **报红**：`没有变矮（338 → 338）` |
| 仍接密度轴、只把 `16` 改成 `20` | **不报红** |

第二行是**对照**，用来证明这条断言测的是「**有没有接上密度轴**」，
而不是「值是不是 16」—— 否则它就过拟合到具体数值了。

#### 为什么 E2 停在这里（不扩到 `SettingsPage`）

`SettingsPage` 有 23 处手写 `spacing`，是剩下的页面里最多的。
**但继续扩页面不会让体验更一致，只会让不一致更明显：**

```
已经响应 density 的：spacing（两个页面 58 处 + E2 接缝）
完全没响应的：      margin  86 处 literal
                    padding 19 处 literal
                    ↑ 卡片的内边距、四周留白全在这两类里
```

再加第三个页面，用户看到的仍然是「一部分紧、一部分不紧」。
**E2 的价值已经拿到了**：证明了密度轴能接通、能测、能防退步，
并量出了「待办页要变紧必须动表达式里的数字」这个结构性发现。

下一步必须先解决 `margin` / `padding` 的口径 —— 见下面 E7。

#### 走查工具的失败必须传播到退出码（Codex 第 14 轮第 1 节）

`densityshots.py` 第一版**到处只记日志**、最后只检查「两帧稳不稳」：

| 情况 | 第一版 | 现在 |
|---|---|---|
| `store.repaired` 为真 | 只写警告 | **非零退出** |
| 页面找不到 | 记日志后 `continue` | **非零退出** |
| 探针找不到 | 记日志 + 生成 `-1` 记录 | **非零退出，不生成记录** |
| 抓图返回空 | 记日志后 `continue` | **非零退出** |
| 截图存盘失败 | **没检查** `QImage.save()` 的返回值 | **非零退出** |
| 产物不齐 | 没查 | **非零退出**（断言 5 页 × 4 档 = 20 张） |

> **那是一条「假绿路径」**：跑失败了却给出「通过」，
> 比没有检查更糟 —— 它会让人以为验过了。
> 这和本项目一直在防的「恒真断言」是**同一类缺陷的不同形式**：
> 一个是从不失败，一个是失败了不说。

**注入验证（5 组，全部只跑一档以省时间）**：

| 注入 | 结果 |
|---|---|
| 基线（不动） | 退出码 0 |

| 删掉一个**探针** | **报红**，命中 `探针 rightScroll 找不到` |
| 让数据触发 `store.repaired` | **报红**，命中 `数据被判定需要修复` |
| 让抓图返回空 | **报红**，命中 `抓图返回空` |

前三组用**临时 QML 副本 / 坏数据文件**（真源码不动）；
第四组改的是**工具副本的抓图调用**（`grabWindow()` 换空 `QImage`）——
「让真抓图返回空」没有干净的外部办法，所以验的是**检测逻辑会不会报红**，
这一点在注入脚本里写明了，不含糊。

**但把那张截图放大 4 倍看，屏幕上是 `⚠ 还没有配置模型` ——

> 解析结果含换行，不折行会把一个标签断成几行，我自己就被误导过一次：

修的过程中还撞上两个坑，都记在代码里：

### E3【钉死】现阶段**不显示**紧凑模式开关

#### 事实基础（实测，`tools/spacingtest.py`）

```
margin    143 处 = token 54 + literal 86 + seam 2 + indirect 1
padding    22 处 = literal 19 + zero 2 + indirect 1
                     ↑ 移掉 1 处假债后的数（见下面「顺带修的一个缺陷」）
```

**要迁的只有 `literal`：86 + 19 = 105 处。**

按属性名分（决定「四边一起」还是「单侧」）：

| margin 属性 | 处数 | | padding 属性 | 处数 |
|---|---|---|---|---|
| `anchors.margins` | 39 | 四边一起 | `leftPadding` | 14 | 单侧 |
| `anchors.leftMargin` | 21 | 单侧 | `padding` | 4 | 四边一起 |
| `anchors.rightMargin` | 22 | 单侧 | `rightPadding` | 1 | 单侧 |
| `anchors.topMargin` | 3 | 单侧 | | | |
| `anchors.bottomMargin` | 1 | 单侧 | | | |

**`Layout.*Margin` 46 处全是 `token`（`Theme.gap`）** —— 它们在 E1 之前
就接好了，**不在本批范围**。（Codex 第 3 轮说「当前源码中没有发现数值型
`Layout.*Margin`」，实测确认：46 处一处数值都没有。）

#### 规则一：轴的选择和 `spacing` 一样 —— 用 `space()`，不是 `px()`

理由和 E1 完全一致：**裸数字不跟 uiScale**（`anchors.margins: 10` 恒为 10），
所以迁到 `space()`（只接密度轴）保持默认行为。

**不能用 `px()` / `scaledSpace()`** —— 那会让这些边距**突然开始跟
界面缩放**，正是 `scaleSeam` 守的那个洞。

#### 规则二：本批**只动 `literal`**，不碰 `token` / `seam`

那 2 处 `seam`（`Onboarding.qml` 的 `Theme.px(10)` / `Theme.px(26)`）是
**历史遗留**，它们**本来就跟着 uiScale**。要接密度轴得改成
`Theme.scaledSpace(N)`（`density=1` 时逐像素相同）。
**但这属于另一件事**，本批不动 —— 保持「只把裸数字接到密度轴上」这一条。

#### 规则三：成对间距 —— **一起迁，但不强求同值**

数据（全部 12 个文件中所有单侧 `*Margin` / `*Padding`）：

| | 对数 |
|---|---|
| 值**相同**的配对 | 12 |
| 值**不同**的配对 | 10 |
| 只有单侧的 | 16 |

**关键认识：默认档下「成对」根本没有风险。**
`literal 10 → Theme.space(10)` 在 `density=1` 时**逐像素等于 10** ——
左右两边各自保值，值不相等的**也不会变相等**。

风险只在 `density<1`：两边各自乘 density 取整，**原本刻意的差值被压缩**。
实测量化（`Math.round`，JS 语义）：

```
配对                        1.00    0.90    0.80    0.70
TasksPage:149~150          10/38   9/34    8/30    7/27    ← 差 28 压到 20
Dashboard:151~152          16/8    14/7    13/6    11/6
AiHistoryPanel:90~91       10/8     9/7     8/6     7/6    ← 只剩 1px 差
Dashboard:309~310          14/12   13/11   11/10   10/8
```

**没有一对会在四个档位下塌陷成相等**（最薄的是 1px 差）。
但**这必须被断言住**，否则以后有人改了值就可能悄悄塌陷。

> **所以安全规则是「一起迁 + 保证不塌陷」，
> 不是「两边改成同一个值」** —— 后者是改设计。

Codex 说「如果目前没有配对守卫，先不声称它已被自动保护」。
**实测：确实没有。**

人为造出「`leftPadding: Theme.space(11)` + `rightPadding: 11`」
（左迁了、右没迁）之后：

```

densitytest.py   退出码 0，变红 0 条
```

原因很直接：扫描器按「**处**」计数，它不知道 `leftPadding` 和
`rightPadding` 是一对，也就无从判断「只迁了一半」。

所以 `spacingtest.py` 里加了 `PAIR_GUARD_IMPLEMENTED = False` 常量，
**并且每次输出都打印这个警告** —— 免得以后有人以为成对间距被守住了。
成对规则（E6、本节规则三）**靠人审**。要变成自动守卫需要按「对」建模，
那是**口径变更**，得双方同意。

##### 两个技术障碍（都实测过，记下来免得重踩）

**一、`anchors.margins` 从 PySide6 读不到。** 它是 QML 的**分组属性**：

  · `item.property("anchors")` → `RuntimeError: Can't find converter
    for 'QQuickAnchors*'`
  · `QQmlExpression(ctx, item, "anchors.margins").evaluate()`
    → 遍历 1970 个项，**全部返回空**

改用**等价的可测量**：`anchors.fill: parent` + `anchors.margins: N`
意味着 `宽度 = 父宽 − 2N`，而 `width` 是普通属性、读得到。
给 `NotesPage` 内层布局加了 `objectName: "notesInner"`，实测：

```
density   1.00 → 0.90 → 0.80 → 0.70
宽度       190    192    194    196      ← 边距收紧，宽度变大
```

**二、像素比较必须先量「噪声地板」。** 同一份源码连续渲两次**也会差**
（抗锯齿、动画残留）。`pxdiff.py` 第一版直接比「迁移前后」，
得到 tasks 430 / settings 258 像素差异，**看起来像有缺陷** ——
而同一份源码两次也差 430 / 754。

所以判据是「迁移差异 ≤ 噪声地板 × 2 + 底噪」，而不是「差异 == 0」。
**而且容差本身要被检查**：加了 `MAX_TOLERANCE_RATIO = 2%` 的断言，
拦「容差大到没有判别力」的情况 —— `ai` 页曾测出 4.5%（切页时导航项的
`ColorAnimation` 没停），那种容差下断言等于没写。

实测结果：

| 页面 | 噪声地板 | 迁移差异 |
|---|---|---|
| tasks / notes / reminders / ai | 0~15 | **0** |
| settings | 617~951 | 588~682（在噪声内） |

**另外两个坑**：

  · **底部状态栏画的是数据目录路径** —— 每个渲染各建一个目录时，
    三个页面都差 ~2340 像素，全是那行路径文字。必须用**同一个**数据目录
  · **`today` 页有实时时钟** —— 两次渲染之间跳一秒就是 19 万像素不同
    （占整屏 30%）。它只比结构量，不做像素比较

##### 二、棘轮的一个**设计弱点**：基线滞后不会报红

#### 批 3 的守卫：`tools/pairguard.py`（显式清单，不是通用推断）

Codex 第 12 轮划的边界很关键：

> 我不要求现在改变 `spacingtest.py` 的全局配对口径，也**不要求实现一个
> 依赖启发式方向词匹配的通用守卫**；那会扩大测试口径并重新引入错配风险。
> 但批次 3 的 10 对值不同边距不能只靠人工看提交信息。
>
> 这**不是通用配对建模**，而是 10 对已审计对象的**窄范围回归守卫**。

所以清单是**人工审计出来后写死**的（文件 + 行号 + 两侧属性 + 原始值），
放在 `PAIRS` 常量里。**不靠方向词替换去找配对** —— 那条路已经错过一次：
`anchors.rightMargin` 的 `right` 被换成 `left` 就去匹配 `leftMargin`，
**错配到别的属性上**，导致 2 处单侧漏统计。

##### 它和 `pairsafe.py` 的分工

| 工具 | 管什么 |
|---|---|
| `pairsafe.py` | **值**在四个 `density` 档位下会不会**塌陷**（纯算术，不看源码） |
| `pairguard.py` | **源码**里两侧的写法是否**同步**（读真实 QML） |

**两件事，两个工具，不能互相替代。**

##### Popup 成组检查（Codex 第 12 轮第 2 节的硬要求）

> Popup 的 `padding` 和 `implicitHeight` 必须一起验证，**不能只让扫描器的
> `padding literal` 归零而留下未接密度轴的 `+ 8`**。

**为什么必须单独查**：扫描器只看得见 `padding:` 属性，
`implicitHeight: contentItem.implicitHeight + Theme.space(8)` 里那个 `+ 8`
是**表达式内的数字**，扫描器**看不到**。
所以「`padding literal = 0`」**不能证明** Popup 接上了密度轴。

##### ⚠️ 一个反直觉的点：`padding: 4` 迁了但**永远不会缩**

```
density           1.00   0.90   0.80   0.70
Theme.space(4)       4      4      4      4     ← 小值门槛，恒定
+ Theme.space(8)     8      7      6      6     ← 会缩
```

**成组迁移之后，Popup 的高度变化全部来自 `+ 8`。**
那两处 `padding: 4` 在**计数**上是真进度（接上了密度轴），
但在**用户感知**上**没有变化**。这两件事要分开说。

##### 六组注入验证（**全部在临时副本上做**）

按 Codex 要求「用临时副本注入『只迁一侧』的故障」，
`pairguard.py` 支持 `PAIRGUARD_ROOT` 环境变量覆盖根目录 ——
注入脚本复制涉及的文件到 `.cache/pairguard-copy/`，改副本再跑，
**真源码全程未被碰过**。

| 注入 | 结果 |
|---|---|
| 基线（副本不改） | 退出码 0 |
| 1. **只迁一侧**（左 `Theme.space(12)`、右裸 `10`） | **报红**：`两侧形态一致（左 spaced / 右 raw） **只迁了一侧**` |
| 2. 数值写错（`10` → `11`） | **报红**：`左侧值 = 10（raw） 实际 11` |
| 3. 清单项缺失（删掉一个文件） | **报红**：`文件不存在` |
| 4. **对照**：两侧**都**迁 | **不报红** ✓ |
| 5. Popup 的 `+ Theme.space(8)` 退回裸 `+ 8` | **报红** |

**第 4 组是对照** —— 它证明守卫测的是「**同步**」，而不是「必须保持裸数字」。
没有这一组，我可能写出一个「只要迁了就报红」的假守卫，
那样批 3b 正常完成反而会被判失败。

**第 5 组是关键**：Popup 的 `+ 8` 退回裸数字时，
**扫描器的数字完全不变**（它看不见表达式里的数字），
只有 `pairguard.py` 能发现 —— 这正是 Codex 担心的情形。

`PHASE` 从 `"3b-pending"` → `"done"`（批 3b 完成后）。

#### 顺带修的一个缺陷：扫描器把「读属性」当成「写属性」

审计时发现的（`PawSwitch.qml:18`）：

```qml
x: control.text.length > 0 ? control.leftPadding : 0
                               ^^^^^^^^^^^^^ 曾被数成「一处 padding」
```

这是**读**一个属性的值，不是**写**它。旧正则的前瞻是
`(?<![A-Za-z_])` —— 只管字母和下划线，而 `.` 不是字母，于是匹配上了。

**为什么必须修**：这类「债」在迁移时**无处可改**，
棘轮会盯着一个永远降不下去的数字 —— **那是假债**。

修法是前瞻加上 `.`（`(?<![A-Za-z_.])`）。**副作用检查过**：
`anchors.margins` / `Layout.leftMargin` 这些**属性名本身带点**的写法
不受影响 —— 看的是属性名**开头**前一个字符，而它们前面是行首空白。

影响面：`padding` 的零值 3 → 2，总量 348 → 347。
**棘轮基线不变**（去掉的是 `zero`，不进棘轮）。

`spacetest.py` 加了一节（第八节，11 条断言）：三种误报形态必须
**不计入**、五种真赋值必须**仍然计入**、以及一行里「先写后读」
**只算一次**；再加一条**对照** —— 用旧正则跑真实的误报行，
证明这条断言确实在测「排除点号」。

#### 定位结论：**屏幕上没有显示标签**

| 查了什么 | 结果 |
|---|---|
| 那一行的来源 | 我的报告 `_count_clipped()`，它记的是 **`text` 属性** |

| `controller.py` 三条路径 | 都是 `to_qt_html(text)`（**text 是原文**），无双层转换 |

**所以「屏幕上显示原始 HTML」这个结论站不住 —— 是报告措辞造成的假信号。**

#### 新增回归：`tools/mdvisibletest.py`（43 项）

虽然前提错了，**断言本身仍有价值** —— 它守的是真实存在的转换链路：
真实用户文本（多行错误消息、Windows 路径、粗体、行内代码、列表、
引用、代码块、省略号、`<Enter>` 这种尖括号词、HTML 实体）
经 `to_qt_html` / `to_plain` 之后，**用户能看到的字符里不该有标签**。

**并且带三组判别力对照**，证明它不是恒真断言：

  · 对照 A：把 HTML 当纯文本显示 → **检出标签**
  · 对照 B：`to_plain(<html>)` → **检出标签**
  · 对照 C：**双层转换** `to_qt_html(to_qt_html(x))` → **检出标签**

同时还**断言了那两条风险当前不可达**（扫 `controller.py`，
确认没有 `to_qt_html(<已有的 html>)` / `to_plain(<已有的 html>)`）——
所以它们只作为「检测有判别力」的证据，不是待修缺陷。

#### 顺带确认的一条真实行为（**不是缺陷**）

`to_qt_html` 生成的是 **Qt 富文本 HTML**，`textFormat: Text.RichText`
下 Qt 解析正常。`"⚠ "` 前缀**不会**破坏解析（实测
`"⚠ " + html` 解析后 123 字符完整）。

#### 一个副作用：`setHtml` 对纯文本会**吃掉内容**

所以**不能**「总是 `QTextDocument.setHtml()`」来取可见文本：

```
'如果 3 < 5 且 a > b'  →  '如果 3 b'
'用 <Enter> 确认'      →  '用 确认'
```

必须先知道 `textFormat`。这条实测结论写在 `tools/densityshots.py`
的 `_visible_text()` 注释里。

### V8 工具链的默认行为会**静默改数据** —— 用它之前先量它

V7 是「手段**看不到**目标」，V8 反过来：手段看到了，
**但看到的是被它自己改过的东西**。

**发现过程。** 核对 `tools/uploadtest.py` 的行数时，`read` 工具和 git
都说 `729` 行，PowerShell 的 `Get-Content` 说 `645`。第一反应是
「文件被改坏了」—— 于是先做了一次裁决：

```
Python    : 36439 字节   sha256 d99bb30f48505867…
PowerShell: 36439 字节   sha256 d99bb30f48505867…
```

**同一个文件的哈希完全一致。** 所以不是文件的问题，是**读数的人**的问题。

**根因**：这个 harness 里的 `pwsh` 实际是 **Windows PowerShell
5.1.22621.6133（Desktop 版）**，不是 PowerShell 7：

```
PSVersion : 5.1.22621.6133
PSEdition : Desktop
```

而 PS 5.1 的 `Get-Content` 对**不带 BOM** 的文件默认按**系统 ANSI
代码页**（中文 Windows = GBK/936）解码。于是 UTF-8 中文被当成 GBK 读：

| 读法 | 结果 |
|---|---|
| `Get-Content -Raw` | **31417 字符**（文件真实是 36439 字节） |
| `Get-Content` | **645 行**（比真实少 84 行） |
| `Get-Content -Encoding UTF8` | **729 行** ✓ |
| `.NET ReadAllLines()` | **729 行** ✓ |
| Python `read_bytes()` | **729 行** ✓ |

那 84 行**不是丢了，是被粘到上一行去了**：GBK 是双字节编码，见到前导字节
（`0x81`–`0xFE`）就吃掉下一个字节当第二个字节。UTF-8 的中文是 3 字节，
按 GBK 解就成了「一个双字节字 + 一个光杆前导字节」，**多吞一个字节** ——
如果被多吞的那个正好是换行符 `0x0A`，这一行就和下一行粘在一起。

最直接的证据：`Get-Content[644]` 取出来正好是整个文件的**最后一行** ——
它读全了，只是**数不对**。

> ⚠️ 这种错误**不报错、不警告**。你拿到的是一个看起来正常的行数、
> 一段看起来正常的文本（只是中文是乱码）。

**同一个「默认值问题」在这一轮里咬了源码文件两次**（都不是「忘了」，
是那些 API 的默认行为本身会改文件）：

| 操作 | 悄悄做了什么 | 代价 |
|---|---|---|
| `Set-Content -Encoding UTF8`（PS 5.1） | **加 BOM** | `git commit -F` 把 BOM 读成提交信息的第一个字符 |
| `Path.write_text(text, encoding="utf-8")` | Windows 上把**全部 `\n` 换成 `\r\n`** | 381 行的文件多出 381 字节（15641 → 16019） |

**所以规则是：**

  · 核对文件内容用 **Python（字节层）** 或 `read` / `edit` 工具 ——
    它们和 git 一致（本轮做过三方交叉验证）
  · 非要用 PowerShell，**显式写 `-Encoding UTF8`**
  · **改源码文件不要用 PowerShell 或自写脚本做字符串替换**；
    必须用脚本时走 `read_bytes` / `write_bytes`，不经过文本层

**为什么值得单列**：这不是「某个工具有 bug」，而是
**验证工具本身就是被验证对象的一部分**。用 `Get-Content` 去数行数、
核内容，得到的结论**在工具出错时依然长得像结论** ——
这正是 V7 那句「一个覆盖不到目标的验证比没有验证更糟」的另一种形态。

### V9 断言不要依赖**操作系统级别的时序和焦点**

V1 要求「每阶段跑全量回归」，但**没说过套件本身可能时绿时红**。
这一条来自实测：`tools/interactiontest.py` 在本轮 6 次运行里
**挂了 2 次、过了 4 次，代码没有任何改动**。

| 次数 | 结果 | 挂在哪 |
|---|---|---|
| 全量回归 #1 | 挂 4 条 | 双击三条 + 导航点到 `today` |
| 单独跑 #1 | 挂 4 条 | 同上 |
| 单独跑 #2–#5 | **全过** | — |
| 全量回归 #2 | **全过** | — |
| 全量回归 #3 | 挂 2 条 | 「获得焦点」+ 导航点到 `focus` |

**注意失败点是变动的**（`today` / `focus` / 不同条数）—— 这是时序抖动的
典型特征，而不是固定的逻辑错误。如果是一个真 bug，挂的应该是同一批断言。

（顺带记一个**被证伪的假设**：我一度认为是 `regress.py` 拉起的小爪实例
（`NEEDS_APP`）在屏幕上挡住了点击。查了 `SUITES` 顺序 ——
`interactiontest.py` 在第 96 行，`uia_test.py`（唯一需要实例的套件）
在第 116 行，**那时实例还没起来**。假设不成立，弃掉。
**查顺序这个动作本身就是结论的一部分**，不能靠印象。）

**两个可疑点**（Codex 判为**测试脆弱性**，不是已证实的产品缺陷；我接受，
并按其建议修掉了）：

  · `工作台双击后获得焦点` 读的是 `dashboard.property("active")` ——
    这依赖 **Windows 授予前台激活**。而 Windows 有「焦点窃取防护」：
    非前台进程的激活请求可能被拒（任务栏闪烁代替）。这是一个
    **本质上不确定**的外部条件，断言它就会时绿时红
  · `工作台打开后导航仍可点击` 用的是**写死的像素偏移**：
    `mapToGlobal(QPoint(70, 46 + 12 + 2 * 44 + 20))`。窗口位置/尺寸/
    动画状态稍有不同，点就会落到相邻的导航项上 —— 实测落到了 `focus`
    而不是期望的 `tasks`，**偏差正好是一个导航项的高度**

**这不是「测试写得不好」，是「断言选错了对象」**：它断言的是
**操作系统的行为**（谁能抢到焦点、像素落在哪一项），而不是**产品的能力**
（双击之后工作台有没有打开、导航能不能切页）。后者才是要保的东西。

**修法（已实施）**：
  · 焦点：改成**有界重试**（最多等 2 秒），拿到就过；拿不到**不记为失败**，
    而是打印一条带原因的观察（`[--]` 行），产品级断言靠
    「工作台已显示 / 指令栏已收起 / 碰撞箱已暂停」这三条
  · 导航：给 Repeater delegate 加稳定的 `objectName`（`nav_<key>`），
    测试读**真实控件的中心点**再点击，不再推算坐标

#### 修的过程中又踩到一个坑，值得单独记

加了 `objectName` 之后，测试里 `findChild(QObject, "nav_tasks",
Qt.FindChildrenRecursively)` **仍然返回 None**。

我先按「名字没设上」查（给 delegate 设一个静态名字做 A/B）——
A/B 两边都找不到；又按「delegate 没实例化」查（`itemAt(0)` 返回 None、
`children()` 里只有 `QQmlComponent` 和 `QQmlDelegateModel`）——
**两次推断都是错的**。

真相是**遍历方式**：**Repeater 生成出来的 delegate，QObject 父子关系和
视觉父子关系不一致**。

| 遍历方式 | 结果 |
|---|---|
| `findChildren(QObject)`（QObject 树） | **找不到**任何 `nav_*` |
| `childItems()`（视觉树） | 7 个全在，名字和坐标都对 |

```
nav_today y=0 / nav_focus y=44 / nav_tasks y=88 / nav_notes y=132
nav_reminders y=176 / nav_ai y=220 / nav_settings y=264
```

而**布局早就说明它们存在**：侧边栏那个占位 `Item` 落在 `y=308`，
正好等于 `7 × 44` —— 这个数字我一开始看到了却没往「delegate 存在」上想。

测试里现在用 `find_visual()` 递归走 `childItems()`，并把
`findChild 找到=False，视觉树找到=True` 打进输出 ——
**让下一个读的人直接看到这个差异，而不是再踩一次。**

> **一条时绿时红的断言，比一条从不失败的断言更难发现** ——
> 它偶尔会红，所以看起来「在工作」；单次通过又会被当成没问题。
> **判据是「限定条件下可重复」，不是「跑过一遍是绿的」。**

## 附录：对比度怎么算（A2b 用）

WCAG 2.x 的相对亮度和对比度。**不要用「看着差不多」代替计算** ——
「深色模式下这块发灰」这种判断，肉眼看不出是 2.9 还是 3.1。

```python
def srgb_to_linear(channel: float) -> float:
    """sRGB 分量（0~1）→ 线性光。注意是分段函数，不是简单的 2.2 次方。"""
    if channel <= 0.04045:
        return channel / 12.92
    return ((channel + 0.055) / 1.055) ** 2.4


def luminance(hex_color: str) -> float:
    """#rgb / #rrggbb / #aarrggbb 都收（#aarrggbb 是 QML 的写法，要跳过前两位）。"""
    text = hex_color.lstrip("#")
    if len(text) == 3:
        text = "".join(char * 2 for char in text)
    if len(text) == 8:                      # aarrggbb
        text = text[2:]
    red = srgb_to_linear(int(text[0:2], 16) / 255.0)
    green = srgb_to_linear(int(text[2:4], 16) / 255.0)
    blue = srgb_to_linear(int(text[4:6], 16) / 255.0)
    # 系数是按人眼感光灵敏度来的：绿最亮，蓝最暗
    return 0.2126 * red + 0.7152 * green + 0.0722 * blue


def contrast(foreground: str, background: str) -> float:
    first, second = luminance(foreground), luminance(background)
    lighter, darker = max(first, second), min(first, second)
    return (lighter + 0.05) / (darker + 0.05)
```

参考值（正文 4.5:1、大字 3:1 是 WCAG AA）：

| 谁 | 门槛 |
|---|---|
| 正文（`fsBody` 及以上） | 4.5:1 |
| 大字（约 ≥ 18px 或粗体 ≥ 14px） | 3:1 |
| 次要/最弱文字（本项目定为装饰性信息） | 3.0:1 |
| 图形元素（图标、开关圆点、边框） | 3:1 |

**这套配色是粉彩风格，白色画在任何粉彩上都到不了 4.5:1** ——
所以 A2c 那个问题（用户消息气泡）不是计算错了，是配色风格本身的取舍。
新预设如果也想走粉彩，就要接受「粉彩底上用深色文字」这个前提。

第二次错得更隐蔽：**字面量搜索只能否证关于字面量的论断**，
而我要否证的是**渲染出来的颜色**。`PawButton._fg` 是个 `switch`
表达式，实际返回 `"#ffffff"`，但搜索搜不到 —— 它不是字面量出现，
是计算结果。

于是：

- 我的**原始担心是对的**（accent 2.38:1、violet 2.74:1、rose 3.29:1）
- 我的**「纠正」是错的**，而且因为它带着「我做了验证」的权威感，
  比第一次的错更危险
- **Codex 找到了真正的答案**：字面量 2 处 + 动态 3 处

教训不是「要验证」（我验了），而是：

> **验证手段的覆盖范围，决定了它能支持什么结论。**
> 用「搜字符串」去核对「计算出来的值」，得到的"没有"是假阴性。

这和 V2 那条是同一件事的两面：V2 说「一条从不失败的断言比没有断言更糟」，
这里是「一个覆盖不到目标的验证比没有验证更糟」—— 因为它会**主动**
把一个正确结论推翻掉。

### 第四条和前面三条成因不同

前三条是**判断错了**（把假设当事实、方法覆盖不到）；第四条是
**措辞把「暂缓」写成了「放弃」**。

技术上没错，但传达错了，代价一样大 —— 下一个人读到「本轮不做」
会以为这件事不用再想。**写结论时要问一句「这句话会被读成什么意思」。**

### 第五条：两个成因被合并成了一个

这一条是 Codex 让我把间距数字固化进扫描器时**顺带暴露出来的**。

原来那句话是：

> `Select-String` 默认不区分大小写 …… 得出 `177`；
> 固定口径的扫描器 …… 得出 `164`。**差 13 处，全部来自工具默认行为。**

但**同一个文件的 docstring 里写的是另一组数**：`169 vs 177` —— 差 **8**。

两组数不是一回事，我把它们当成一个了：

| 比较 | 差额 | 成因 |
|---|---|---|
| `169` → `177` | **8** | 只换了大小写（`bodySpacing` 被算进来） |
| `169` → `164` | **5** | 换了口径（剥离注释、把 `0` 和间接值分出去） |
| `177` → `164` | **13** | 上面两个**叠在一起**，不是同一个原因 |

今天独立复测（`spacing\s*:` 扫全部 QML）：

```
区分大小写   : 182
不区分大小写 : 190      ← 差 8，和早先那次完全一致
默认解码(GBK): 182
-Encoding UTF8: 182     ← 编码差 0
```

**所以「全部来自不区分大小写」是错的**：大小写固定解释 8，剩下的 5
属于口径变化。更深一层的框架错误是：**拿 `literal` 这个子集（164）
去比一个总数（177）**，两者本来就不该相等。

**教训和第三条同类但更细**：不是「没验证」，是**验证做了，但把两个
自变量的效果算到了一个头上**。做对比实验时，一次只应该动一个变量 ——
我动了两个（大小写 + 口径），然后把差额全记在第一个上。

（顺带记一条**没成立**的猜想：我一度以为 PowerShell 的 GBK 解码
也影响了这个计数，因为发现 `Get-Content` 会少读行。实测**编码差 0** ——
粘行不改变模式出现次数。猜想被自己的测量否掉了，所以没写进结论。
详见 V8。）
