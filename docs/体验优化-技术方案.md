## 二、阶段 A：主题预设

### A0【钉死】预设是**数据**，接缝在 `theme.resolved()`

三层叠加，顺序固定：

```
default_overrides()      ← 现有 17 项的默认值（粉白暖色）
      ↓
preset_colors(name)      ← 新增：浅色 / 深色 / 护眼 … 各一份完整表
      ↓
theme.json 的用户覆盖     ← 现有机制，优先级最高
```

新签名 `resolved(overrides, preset="default")`。**后端仍是唯一事实来源**
（`backend.themeColors` 的 docstring 已经这么写了）。

**为什么不把预设写进 QML。** QML 的 `pick(key, fallback)` 里那些字面量是
「backend 还没建好那一瞬间」的兜底，不是配置。把预设也放进去会得到**两份
事实来源**——而深色预设下 QML 兜底是浅色，一旦哪边漏了就是白屏闪烁。
这个项目在「同一个值存两份」上已经栽过三次（重复方式映射、套件清单、
版本常量），不要再来第四次。

### A1【钉死】`ROLES` 必须等于 `pick()` 读的键集合

现状 19 ≠ 17，`rose` / `roseSoft` 是**改了没用的死选项**。

**修法：从 `ROLES` 里摘掉它们，不是让 QML 去读。**

理由：`Theme.qml:60` 的注释已经写明了这是刻意的设计——

> `rose / roseSoft 刻意不开放：错误色如果被改成和背景相近，用户就看不到失败了。`

这是安全决策，尊重它。反过来的做法（开放它）等于让用户能把「失败」调成看不见。

**同时加不变量测试**：`ROLES` 的键集合必须**恰好等于** QML 里 `pick()` 的键集合。
这类「界面承诺了但后端不生效」必须由测试挡住，不能靠人记得同步。

### A2【钉死】预设必须**完备**，靠测试保证，不靠运行时兜底

每个预设必须给出**全部** 17 项。缺项在运行时不会报错——`pick()` 会退回
QML 里的浅色字面量，表现出来只是「深色模式下某块是白的」，很难发现。

纯数据测试（不需要起界面）：

```
对每个预设：
  · 键集合 == ROLES 键集合（缺一个就红）
  · 每个值通过 is_valid_color()（格式）
```

### A2b【钉死】对比度门槛用**棘轮**，不用绝对值

**这一条我改过两次，两次都是因为先写结论再验证。**

第一版写的是「正文 ≥ 4.5:1、次要 ≥ 3:1」，但算了一遍发现
**默认主题自己过不了**（下面有表）—— 拿一个产品当前达不到的标准去要求
新预设，是在挖坑：要么 Codex 违反规则，要么被迫改默认配色，
而那不是他的任务。

第二版我把「白字 on accent/violet/mint/gold」四行都列成不达标。
**又错了**：那四个是我按「按钮上可能有白字」推的，实际全班代码里
白字只有 2 处（见 A2c）。**假设出来的问题不该写成既有缺陷。**

实测当前默认主题（WCAG 对比度，公式算的）：

| 配对 | 实测 | AA | 说明 |
|---|---|---|---|
| `text` on 四种底色 | 8.82 ~ 10.49:1 | 4.5 | 达标 |
| `textDim` on 四种底色 | 4.41 ~ 5.25:1 | 3.0 | 达标 |
| `textFaint` on `bg`/`surface`/`surfaceAlt` | 3.13 ~ 3.44:1 | 3.0 | 达标 |
| `textFaint` on `surfaceHi` | **2.89:1** | 3.0 | 差一点 |
| 白字 on `violet`（用户消息气泡） | **2.74:1** | 4.5 | 见 A2c |

门槛这样定：

```
文字类（text / textDim / textFaint on 四种底色）：
    ≥ 3.0:1，且不低于当前默认主题的同项
其余任何「前景画在背景上」的配对：
    不低于当前默认主题的同项（棘轮，不倒退）
```

即：**新预设不许比现状更差**，文字类另加绝对下限 3.0。可达，
且能防止新预设引入「深色下更看不清」。

**对比度用公式算，不靠肉眼。** 公式见附录。

### A2c【开放·已核实的既有问题】用户消息气泡的白字只有 2.74:1

`AiBubble.qml:90` —— 用户自己发的那条消息是**白字画在 `Theme.violet`
（#b48ae0）气泡上**，对比度 **2.74:1**（AA 要求 4.5）。

这是现在就有、和加预设无关的可读性问题。有一点讽刺：**用户自己的话
比小爪的回复更难读**（助手气泡是深色 `text` on 浅底，9~10:1）。

根因：`violet` 是粉彩（pastel）色，粉彩和白色天生对比度低。
标准解法是在粉彩上用**深色**文字而不是白字。

**本轮不修**（改默认配色属于产品改版）。但：

- **A2b 的棘轮保证新预设不会让这个数字更糟。**
- 如果 Codex 认为顺手修更划算（比如预设体系本来就要重选主色），
  可以提 —— 波及面已经核实过：**只有这一处**。
  `PawSwitch.qml:36` 那处白字是**滑块圆点**（图形元素），
  不适用文字对比度，别把它一起算进来。

**另外记一条给以后：** `AiBubble.qml` 里那段注释（第 99~108 行）记着
这个气泡踩过的四个布局坑（高度与宽度互锁成环、连续换内容时高度不刷新
…）。**改它的任何尺寸都要先读那段注释。**

### A3【开放】预设的具体色值与数量

浅色 / 深色 / 护眼是用户提的，还可以有别的。**色值我不定**——
这是审美判断，Codex 定。我只有一个约束：A2b 的对比度门槛必须过。

### A4【钉死】用户改过颜色之后切换预设的行为

三种可能，我定第一种：

1. **预设是底，用户覆盖在其上**。切预设时保留 `theme.json`（用户的覆盖继续生效）。
   设置页明确显示「已基于【深色】自定义 N 项」+ 一个「恢复此预设」按钮。
2. 切预设时清空用户覆盖。（简单，但用户调了半天的颜色突然没了）
3. 每个预设各存一份覆盖。（复杂度爆炸，45+17×N 个键）

选 1 的理由：现在 `theme.describe()` 已经在做「只说真的和默认不一样的项」，
这个语义直接能复用。用户知道自己在预设之上改了什么，也能一键退回去。

## 三、阶段 B：AI 页折叠

### B1【钉死】用共享组件，不用每面板各写一份展开状态

新增 `CollapsibleSection.qml`，注册进 `qmldir`（和 `Card` 同级）。

理由：四个面板（`AiSettingsPanel` / `AiMcpPanel` / `AiHistoryPanel` /
`PermissionCard`）现在是独立组件，但**折叠是同一件事**。四份展开状态
意味着四处可能不一致（动画时长、箭头方向、点标题还是点箭头、键盘可达性）。

#### 先说清楚：已有的两套「折叠」和这个不是一回事

代码里已经有类似机制，我核实过它们的语义，**别把它们当成同一个东西合并**：

| 现有机制 | 位置 | 实际语义 |
|---|---|---|
| `page.showHistory` → `AiHistoryPanel.expanded` | `AiPage.qml:21,354` | **整张卡片显示/隐藏**，由页面上的按钮切换（第 328~330 行） |
| `page.showMcpDetail` → `AiMcpPanel.showDetail` | `AiPage.qml:27,457` | 卡片内**详细区**的开关 |

本方案要的是第三种：

```
CollapsibleSection：卡片**始终可见**，默认只显示标题栏，
                    点标题（或箭头）展开正文
```

三者的区别是实质性的：前两种是「这块内容要不要出现」，
第三种是「这块内容以什么形态出现」。**统一它们属于范围外**，
真要动的话单独提。

`AiHistoryPanel` 的 `expanded` 属性名和第三种语义撞了，
实现时注意别混（必要时改名，但那是它自己的事）。

### B2【钉死】v1 **不新增 settings 键**，展开状态只在会话内记忆

理由：`settings` 已经 45 个键，而展开状态是**可重新推导的廉价状态**。
加进去会：让设置项继续膨胀、让「恢复默认」要处理它、
让导入导出多一份要迁移的数据。

会话内记忆（页面级属性）就够了：切页回来还是展开的，重启回到默认。

**【开放】** 默认展开哪些。我的建议：只展开第一个，其余收起——这样
380×330 的视口一屏内能看到全部标题（用户知道有什么），而不是看到
第一块就被淹掉。

### B3【钉死】折叠的收益必须量化断言

这是我测出来的数字，可以直接当验收标准：

```
工作台 860×560 → AI 页 Flickable：
  改动前 contentHeight = 2025px（6.1 屏）
  验收：默认状态（全部收起）contentHeight < 900px
```

**不是「看起来好点了」，是一个能红的数字。** 这类布局改动没有视觉回归
设施，只能靠量化守住。

## 四、阶段 C：待办批量编辑

### C1【钉死】选择态在**视图层**，不在模型层

「哪些被勾选了」是 QML 属性，不是 `TaskModel` 的字段。

理由：`TaskModel` 同时被 AI 工具驱动（`ai/tools.py` 里有待办工具）。
选择态一旦进模型，一次 AI 调用就可能改变用户正在勾选的东西——
用户勾了 5 条准备删，AI 顺手加了一条待办触发了 `_rebuild`，
勾选状态错位，**用户删掉的不是他想删的**。

### C2【钉死】批量操作是一次落盘，不是 N 次

新模型槽收 `list[str]`（id 列表），内部**只调一次 `_touch()`**。

一次 `_touch()` = 一次 `store.save()` + 一次模型重置 + 一次信号。
删 20 条如果走 20 次单条接口，就是 20 次全量写盘（对话历史那条经验：
全量重写是 O(文件大小)）。

### C3【钉死】撤销语义扩展为「**最后一次操作**」，批量的整体撤销

现在 `_last_removed` 只存一条。批量删除之后，用户按「撤销」期望的是
**恢复刚才删掉的那一批**，不是恢复其中一条。

所以语义统一成「撤销上一次操作」：

```
_last_removed: 单条删除 → 一个元素
               批量删除 → N 个元素
               撤销     → 一次性全部恢复
```

**不做多级撤销栈。** 用户真正会用的就是「我刚才删错了」这一种；
栈会带来「撤销到第几步了」的界面负担。这个取舍之前已经定过一次
（单个模型时），批量沿用同一个。

### C4【开放】批量编辑的交互形式

复选框常驻 / 长按进入选择模式 / 工具条切换。**这是产品判断，Codex 定。**
我只要求：进选择模式后「全选」「批量完成」「批量删除」三个动作可达，
且退出选择模式的路径明确（不能进了出不来）。

**已知约束**：`TasksPage.qml` 现在**没有任何多选代码**（`selected` /
`multiSelect` / `checkedIds` 全是 0 处命中），所以是从零加，不是改。

## 五、阶段 D：设置分层

### D1【钉死】`advanced_mode` 的准入用**规则**，不用逐个拍脑袋

现在只门控 2 处。扩展时必须有可复述的判据，否则会变成「谁顺手谁加」。

规则：

> 一个设置项进 `advanced_mode`，当且仅当它**同时**满足：
> 1. 泛用户不需要改（默认值对大多数人是合适的）
> 2. **改错的代价 > 用不上的代价**
>
> 典型的第 2 条：需要外部前置条件（API Key、MCP 服务器、知识库文件），
> 或者改了之后在界面上看不出效果。

反例（**不该**进门控）：`pet_scale`、`notifications`、主题预设——
泛用户会想改，而且改错了当场看得见。

### D2【开放】按规则给 45 个设置项分类

我给规则，Codex 执行分类并给出清单。**分歧点应该在具体项上，不在规则上** ——
如果觉得规则本身有问题，先改规则再分类。

### D3【钉死】分层要有量化验收

```
默认（advanced_mode = false）状态下：
  设置页可见的 PawSwitch + PawSlider + PawField + PawButton 数量
  必须比改动前下降 ≥ 25%
```

理由同 B3：没有视觉回归设施，只能靠数字。而且这个数字能防止
「加了门控但其实只藏了一个开关」这种自我安慰式的改动。

## 六、阶段 E：紧凑模式 —— **本轮不做**

### E0【钉死】紧凑模式**不是** `ui_scale` 的复用

`Theme.px(v) = round(v * scale)`，而 `scale` 来自 `backend.uiScale` ——
**间距和字号共用同一个系数**。它是「整体缩放」（给看不清的人用的），
不是「紧凑」（给想一屏看更多的人用的）。

紧凑要的是**间距降、字号不变**，所以必须是**独立轴**：
新增 `Theme.density`，只乘间距类 token（`gap` / `gapLg` / `pad` /
`radius*`），**不乘** `px()` 本身（它有 78 个调用点，混着字号和间距）。

### E1【钉死】紧凑模式的**前置条件**是间距 token 化

```
走 Theme token 的间距： 65 处
写死数字的间距：      201 处   ← 75.6%
```

现在做紧凑模式，只有约四分之一的界面会跟着变 —— 结果是
**又紧又不紧**，比不做更糟。

所以先还债，用**棘轮测试**（ratchet）而不是一次性全改：

```
断言：写死的间距数量 ≤ 上一次记录的值
      目标：单调下降，直到 0
```

棘轮的理由：201 处分散在约 20 个文件，一次性改的风险是布局悄悄坏掉，
而**我们没有视觉回归设施**能抓住「这个卡片间距变得很怪」。
棘轮让这笔债可以分批还，且不会倒退。

**这一阶段的启动条件是 E1 完成。本轮不做，先记在这里。**

## 八、验证协议（对协作双方的约束）

这一节是**流程要求**，不是建议。本项目在这些点上已经栽过跟头。

### V1 每个阶段必须有断言，且登记进 `tools/regress.py` 的 `SUITES`

`SUITES` 是**唯一清单**，`build.py` 从它导入。**没登记的测试永远跑不到** ——
写多少都等于没写。（曾经打包前自测的清单比实际回归少 9 个套件，
于是 QML 语法错误能打进包里发出去。）

### V2 断言必须**被证明能抓住目标 bug**

写完断言之后，**故意把产品代码改坏**，确认断言变红；还原。

本项目栽过两次，两次都是「断言看起来在测，其实什么都没测」：

- 贴边朝向的断言读的是**测试自己写的常量**，把产品里的符号改反它照样全绿
- 上传工具第一版断言取错了键，在比较 `"" == ""`

> **一条从不失败的断言比没有断言更糟** —— 它给的是虚假的安心。

## 附录：对比度怎么算（A2b 用）

WCAG 2.x 的相对亮度和对比度。**不要用「看着差不多」代替计算** ——
「深色模式下这块发灰」这种判断，肉眼看不出是 2.9 还是 3.1。

```python
def srgb_to_linear(channel: float) -> float:
    """sRGB 分量（0~1）→ 线性光。注意是分段函数，不是简单的 2.2 次方。"""
    if channel <= 0.04045:
        return channel / 12.92
    return ((channel + 0.055) / 1.055) ** 2.4


def luminance(hex_color: str) -> float:
    """#rgb / #rrggbb / #aarrggbb 都收（#aarrggbb 是 QML 的写法，要跳过前两位）。"""
    text = hex_color.lstrip("#")
    if len(text) == 3:
        text = "".join(char * 2 for char in text)
    if len(text) == 8:                      # aarrggbb
        text = text[2:]
    red = srgb_to_linear(int(text[0:2], 16) / 255.0)
    green = srgb_to_linear(int(text[2:4], 16) / 255.0)
    blue = srgb_to_linear(int(text[4:6], 16) / 255.0)
    # 系数是按人眼感光灵敏度来的：绿最亮，蓝最暗
    return 0.2126 * red + 0.7152 * green + 0.0722 * blue


def contrast(foreground: str, background: str) -> float:
    first, second = luminance(foreground), luminance(background)
    lighter, darker = max(first, second), min(first, second)
    return (lighter + 0.05) / (darker + 0.05)
```

参考值（正文 4.5:1、大字 3:1 是 WCAG AA）：

| 谁 | 门槛 |
|---|---|
| 正文（`fsBody` 及以上） | 4.5:1 |
| 大字（约 ≥ 18px 或粗体 ≥ 14px） | 3:1 |
| 次要/最弱文字（本项目定为装饰性信息） | 3:0:1 |
| 图形元素（图标、开关圆点、边框） | 3:1 |

**这套配色是粉彩风格，白色画在任何粉彩上都到不了 4.5:1** ——
所以 A2c 那个问题（用户消息气泡）不是计算错了，是配色风格本身的取舍。
新预设如果也想走粉彩，就要接受「粉彩底上用深色文字」这个前提。
