## 审查结论（2026-09-28）

本轮把三个开放项定下来，并修正了四处容易把假设写成事实的地方：

1. **A3：只做 3 个预设**：`default`（柔粉浅色，保留现有风格）、
   `dark`（夜间深色）、`sage`（护眼绿）。不另做一个和 `default` 重复的
   「浅色」预设；`default` 本身就是浅色预设。
2. **C4：选择工具条进入批量模式**。不采用长按（桌面端不可发现），也不让
   复选框常驻（列表默认态会变吵）。进入后提供「全选当前结果 / 完成 / 删除 /
   退出」，`Esc` 也能退出。
3. **A2c：本轮修复**。不仅修 `AiBubble.qml` 的用户消息气泡，也修共享的
   `PawButton.qml` 白字路径。后者之前被「只搜写死的 `#ffffff`」漏掉了，实际
   `primary` / `accent` / `danger` 三种按钮都可能用白字压在低对比度粉彩上。
4. **B1/B3：安全卡片不折叠，验收按状态分层**。`PermissionCard` 在左栏，
   还是高风险操作的常驻入口，不纳入普通信息卡折叠；AI 未配置时设置卡必须强制
   展开，不能为了追求一个总高度数字把用户的配置出口藏掉。

这些结论只改变开放项和实现细节，不推翻数据接缝、批量落盘、撤销语义、
验证协议等结构性决策。

## 二、阶段 A：主题预设

### A0【钉死】预设是**数据**，接缝在 `theme.resolved()`

三层叠加，顺序固定：

```
fixed_colors()           ← rose / roseSoft，永不进入预设或用户覆盖
      ↓
preset_colors(name)      ← 17 项完整表
      ↓
theme.json 的用户覆盖     ← 只覆盖这 17 项，优先级最高
```

`resolved(overrides, preset="default")` 是唯一的最终合成函数。**后端仍是唯一事实来源**
（`backend.themeColors` 的 docstring 已经这么写了）。

### A0.1【钉死】`theme.json` 的兼容格式

新格式如下，预设名和用户覆盖放在同一个文件，避免再增加一个设置键：

```json
{
  "preset": "default",
  "colors": {
    "accent": "#f4879f"
  }
}
```

读取必须兼容现有两种格式：旧的裸颜色映射，以及已有的
`{"colors": {...}}` 包装。读取旧格式时隐式使用 `default`；保存时统一写成
上面的新格式。未知预设名回退到 `default`，同时返回一条可展示的提示，不能
把界面留在半套颜色上。

建议的 Python 接口保持小而明确：

```text
load_config(path) -> {preset: str, colors: dict[str, str]}
save_config(path, preset, colors) -> (bool, message)
preset_colors(name) -> dict[str, str]       # 每次返回副本
resolved(overrides, preset="default") -> dict[str, str]
```

`Backend.themeColors` 继续只暴露 `resolved()` 的结果；另外提供只读的
`themePresets`（名称、中文名、说明）和当前 `themePreset`，设置页切换预设时
只改 `preset` 字段，不把颜色表复制进 `settings`。`resetTheme()` 的语义改为
「恢复当前预设」，另保留一个「恢复柔粉默认」入口，避免用户在深色主题里点
「恢复默认」却突然跳回浅色。

**为什么不把预设写进 QML。** QML 的 `pick(key, fallback)` 里那些字面量是
「backend 还没建好那一瞬间」的兜底，不是配置。把预设也放进去会得到**两份
事实来源**——而深色预设下 QML 兜底是浅色，一旦哪边漏了就是白屏闪烁。
这个项目在「同一个值存两份」上已经栽过三次（重复方式映射、套件清单、
版本常量），不要再来第四次。

### A1【钉死】可变角色必须等于 `pick()` 读的键集合

现状 19 ≠ 17，原因是 `ROLES` 把固定错误色也混在可变角色清单里。
不要只把两个元素从最终颜色表删掉；要把概念拆开：

```text
EDITABLE_ROLES = 17 个可改角色
FIXED_COLORS   = {rose, roseSoft}
PICK_KEYS      = 从 Theme.qml 的 pick("...") 实际解析出的 17 个键
```

不变量改成三条：

```text
keys(EDITABLE_ROLES) == PICK_KEYS
keys(preset_colors(name)) == PICK_KEYS
keys(resolved(...)) == PICK_KEYS ∪ keys(FIXED_COLORS)
```

`rose` / `roseSoft` 仍由 QML 固定写出，也仍由 `resolved()` 返回给需要完整
色表的后端调用者，但它们不出现在 `themeRoles`、预设表或用户覆盖中。

理由：`Theme.qml:60` 的注释已经写明了这是刻意的设计——

> `rose / roseSoft 刻意不开放：错误色如果被改成和背景相近，用户就看不到失败了。`

这是安全决策，尊重它。反过来的做法（开放它）等于让用户能把「失败」调成看不见。

测试必须从 `Theme.qml` 的真实 `pick("...")` 文本解析键集合，不能在测试里
再手写一份 17 键常量；否则把 QML 的 `pick("accent")` 改成拼错时，测试
仍可能拿自己的常量互相比较而全绿。

### A2【钉死】预设必须**完备**，靠测试保证，不靠运行时兜底

每个预设必须给出**全部** 17 项。缺项在运行时不会报错——`pick()` 会退回
QML 里的浅色字面量，表现出来只是「深色模式下某块是白的」，很难发现。

纯数据测试（不需要起界面）：

```
对每个预设：
  · 键集合 == EDITABLE_ROLES / PICK_KEYS（缺一个就红）
  · 每个值通过 is_valid_color()（格式）
```

### A2b【钉死】对比度门槛用**棘轮**，不用绝对值

**这一条我改过两次，两次都是因为先写结论再验证。**

第一版写的是「正文 ≥ 4.5:1、次要 ≥ 3:1」，但算了一遍发现
**默认主题自己过不了**（下面有表）—— 拿一个产品当前达不到的标准去要求
新预设，是在挖坑：要么 Codex 违反规则，要么被迫改默认配色，
而那不是他的任务。

第二版我把「白字 on accent/violet/mint/gold」四行都列成不达标。
**这次复核发现原结论漏搜了共享组件**：字面量搜索确实只看到气泡文字和
开关圆点，但 `PawButton.qml` 的 `_fg` 是运行时返回 `#ffffff`，实际覆盖
`primary` / `accent` / `danger` 三种按钮。因此这是已核实的交互文字问题，
不能继续按「只有气泡一处」处理。

修复前的当前默认主题基线（WCAG 对比度，公式算的）：

| 配对 | 实测 | AA | 说明 |
|---|---|---|---|
| `text` on 四种底色 | 8.82 ~ 10.49:1 | 4.5 | 达标 |
| `textDim` on 四种底色 | 4.41 ~ 5.25:1 | 3.0 | 达标 |
| `textFaint` on `bg`/`surface`/`surfaceAlt` | 3.13 ~ 3.44:1 | 3.0 | 达标 |
| `textFaint` on `surfaceHi` | **2.89:1** | 3.0 | 差一点 |
| 白字 on `violet`（用户消息气泡） | **2.74:1** | 4.5 | 见 A2c |
| `PawButton` 白字 on `accent` / `violet` / `rose` | **2.38 / 2.74 / 3.29:1** | 4.5 | 见 A2c |

门槛这样定：

```
文字类（text / textDim / textFaint on 四种底色）：
    ≥ 3.0:1，且不低于修正后 default 预设的同项
用户消息气泡（readableOn(violet)）和填充按钮文字：
    ≥ 4.5:1
其余任何「前景画在背景上」的配对：
    不低于修正后 default 预设的同项（棘轮，不倒退）
```

即：**新预设不许比修正后的现状更差**，文字类另加绝对下限 3.0，
交互文字单独守 4.5。这样既保留粉彩审美，也不会把可读性债务复制到深色主题。

颜色前景不能在每个调用点凭感觉选。新增 `Theme.readableOn(color)`，在白色
和固定深色 `#211a25` 之间选择对比度更高者，至少用于：

```text
PawButton.qml：primary / accent / danger 的文字与 glyph
AiBubble.qml：用户消息气泡文字
```

这样浅色粉彩、深色主题和用户自定义 accent 都走同一条规则，不再把「白字」
写死在共享按钮里。测试读 QML 运行后的真实 `Text.color`，不能只断言源码
里出现了 `readableOn`。

**对比度用公式算，不靠肉眼。** 公式见附录。

### A2c【开放·本次决定：修复】用户消息与填充按钮的文字对比度

`AiBubble.qml:90` —— 用户自己发的那条消息是**白字画在 `Theme.violet`
（#b48ae0）气泡上**，对比度 **2.74:1**（AA 要求 4.5）。

这是现在就有、和加预设无关的可读性问题。有一点讽刺：**用户自己的话
比小爪的回复更难读**（助手气泡是深色 `text` on 浅底，9~10:1）。复核时
还发现 `PawButton.qml` 的共享 `_fg` 对三种填充按钮都固定返回白色，
默认主题的 `accent` / `violet` / `rose` 分别只有 **2.38 / 2.74 / 3.29:1**。

根因：`violet` 是粉彩（pastel）色，粉彩和白色天生对比度低。
标准解法是在粉彩上用**深色**文字，而不是把背景色硬改成刺眼的深色。

**本轮顺手修复，但不改用户气泡的尺寸链路**：

- `AiBubble.qml` 只把用户文字颜色改为 `Theme.readableOn(Theme.violet)`；
  不改宽度、内边距、高度或 `TextMetrics`，避免重新触发那段布局注释记录的
  四个坑。
- `PawButton.qml` 的三个填充变体统一改用
  `Theme.readableOn(control._bg)`；ghost 按钮仍使用 `Theme.textDim`。
- `PawSwitch.qml` 的白色滑块圆点和 `FocusPage.qml` 的进度头是图形元素，
  不把它们误算成文字对比度问题。

实测目标（启用态、默认字号）：

| 位置 | `default` 修复后 | `dark` | `sage` |
|---|---:|---:|---:|
| 用户气泡文字 on `violet` | 6.18:1 | 7.97:1 | 5.18:1 |
| 填充按钮文字最低值 | 5.15:1 | 5.15:1 | 4.65:1 |

三个预设和用户自定义色都必须通过同一套断言；不能只测三张预设表，
否则用户把 accent 改成浅黄色后问题会重新出现。

**另外记一条给以后：** `AiBubble.qml` 里那段注释（第 99~108 行）记着
这个气泡踩过的四个布局坑（高度与宽度互锁成环、连续换内容时高度不刷新
…）。**改它的任何尺寸都要先读那段注释。**

### A4【钉死】用户改过颜色之后切换预设的行为

三种可能，我定第一种：

1. **预设是底，用户覆盖在其上**。切预设时保留 `theme.json` 中的 `colors`
   （用户的覆盖继续生效）。设置页明确显示「已基于【深色】自定义 N 项」+
   一个「恢复此预设」按钮。
2. 切预设时清空用户覆盖。（简单，但用户调了半天的颜色突然没了）
3. 每个预设各存一份覆盖。（复杂度爆炸，45+17×N 个键）

选 1 的理由：现在 `theme.describe()` 已经在做「只说真的和默认不一样的项」，
只需把比较基准改成当前 `preset_colors(preset)`；用户知道自己在预设之上改了
什么，也能一键退回去。接口改为 `describe(overrides, preset="default")`，
不能继续拿柔粉默认值比较深色预设，否则切到深色后会把整张表误报成「用户改过」。

「恢复此预设」只清空 `colors`、保留当前 `preset`；「恢复柔粉默认」才同时把
`preset` 设为 `default`。两者都必须先写临时文件、替换成功后再发
`themeChanged`，保存失败时界面和摘要都不应假装已经切换。

## 三、阶段 B：AI 页折叠

### B1【钉死】用共享组件，不用每面板各写一份展开状态

新增 `CollapsibleSection.qml`，注册进 `qmldir`（和 `Card` 同级）。

理由：右栏的三个信息面板（`AiSettingsPanel` / `AiMcpPanel` /
`AiHistoryPanel`）现在是独立组件，但**普通信息折叠是同一件事**。共享组件
统一动画时长、箭头方向、标题点击区和键盘可达性，避免三处各自漂移。

`PermissionCard` 不包进这个组件：它在左栏，是权限/高风险操作的安全入口，
无待确认时仍显示当前级别，有待确认时必须保持完整可操作，不能靠折叠把风险
提示和确认按钮藏起来。

#### 先说清楚：已有的两套「折叠」和这个不是一回事

代码里已经有类似机制，我核实过它们的语义，**别把它们当成同一个东西合并**：

| 现有机制 | 位置 | 实际语义 |
|---|---|---|
| `page.showHistory` → `AiHistoryPanel.expanded` | `AiPage.qml:21,354` | **整张卡片显示/隐藏**，由页面上的按钮切换（第 328~330 行） |
| `page.showMcpDetail` → `AiMcpPanel.showDetail` | `AiPage.qml:27,457` | 卡片内**详细区**的开关 |

本方案要的是第三种（仅用于右栏普通信息面板）：

```
CollapsibleSection：卡片**始终可见**，默认只显示标题栏，
                    点标题（或箭头）展开正文
```

三者的区别是实质性的：前两种是「这块内容要不要出现」，
第三种是「这块内容以什么形态出现」。**统一它们属于范围外**，
真要动的话单独提。

`AiHistoryPanel` 的 `expanded` 属性名和第三种语义撞了，
实现时注意别混（必要时改名，但那是它自己的事）。

共享组件的最小接口固定为：

```text
title / subtitle
expanded / expandedChanged
defaultExpanded
contentItem（正文槽）
```

标题栏必须是一个完整的可聚焦按钮区域，鼠标点标题和箭头都能切换；
`Space` / `Enter` 切换，`Esc` 只退出当前折叠焦点，不触发删除或权限动作。
动画只改变正文高度和 opacity，不用 `visible: false` 造成键盘焦点落到隐藏项。

### B2【钉死】v1 **不新增 settings 键**，展开状态只在会话内记忆

理由：`settings` 已经 45 个键，而展开状态是**可重新推导的廉价状态**。
加进去会：让设置项继续膨胀、让「恢复默认」要处理它、
让导入导出多一份要迁移的数据。

会话内记忆（页面级属性）就够了：切页回来还是展开的，重启回到默认。

**本次决定：按配置状态给默认值，而不是死写「第一个」。**

```text
AI 已配置、没有待确认动作：
  历史 / 模型设置 / MCP 详情默认收起；聊天区保持展开。
AI 未配置：
  模型设置强制展开，历史和 MCP 详情收起。
出现待确认问题或权限动作：
  对应卡片强制展开并滚动到可操作位置，不能被默认折叠覆盖。
```

用户在本次打开页面后的展开/收起选择只保存在 `AiPage` 的页面属性里；
切页回来保留，重启回到上面的默认值。未配置状态的强制展开优先级最高，
避免新用户只看到一个空聊天框却找不到 API Key 入口。

### B3【钉死】折叠的收益必须量化断言

这是我测出来的数字，可以直接当验收标准；但必须区分配置状态：

```
工作台 860×560 → AI 页 Flickable：
  改动前 contentHeight = 2025px（6.1 屏）
  已配置 + 无待确认动作 + 默认折叠：contentHeight < 900px
  未配置：模型设置强制展开，单独验收设置卡可见且可操作，
          不用 < 900px 这条把配置入口压没
  有待确认动作：对应卡片可见、按钮可点击，且滚动后不被输入区遮挡
```

**不是「看起来好点了」，是能红的数字和可操作性断言。** `aipreview.py`
必须分别构造「已配置 / 未配置 / 有待确认」三种后端状态；不能只截一个
恰好把设置卡隐藏掉的快照。

## 四、阶段 C：待办批量编辑

### C1【钉死】选择态在**视图层**，不在模型层

「哪些被勾选了」是 QML 属性，不是 `TaskModel` 的字段。

理由：`TaskModel` 同时被 AI 工具驱动（`ai/tools.py` 里有待办工具）。
选择态一旦进模型，一次 AI 调用就可能改变用户正在勾选的东西——
用户勾了 5 条准备删，AI 顺手加了一条待办触发了 `_rebuild`，
勾选状态错位，**用户删掉的不是他想删的**。

### C2【钉死】批量操作是一次落盘，不是 N 次

新模型槽收 `list[str]`（id 列表），内部**只调一次 `_touch()`**。

一次 `_touch()` = 一次 `store.save()` + 一次模型重置 + 一次信号。
删 20 条如果走 20 次单条接口，就是 20 次全量写盘（对话历史那条经验：
全量重写是 O(文件大小)）。

接口只接收 ID，不接收 QML 行号；进入模型后先做去重、空值过滤和
「仍存在于 `store.tasks`」校验。批量完成与批量删除都要在内存中完成整批
变更，最后只调用一次 `_touch()`。批量完成要按「原来未完成」的条数更新
`stats[today].tasks_done`，不能循环调用 `toggle()`，否则既会重复保存，也会
把排序/信号触发 N 次。

### C3【钉死】撤销语义扩展为「**最后一次操作**」，批量的整体撤销

现在 `_last_removed` 只存一条。批量删除之后，用户按「撤销」期望的是
**恢复刚才删掉的那一批**，不是恢复其中一条。

所以语义统一成「撤销上一次操作」：

```
_last_removed: 单条删除 → 一个元素
               批量删除 → N 个元素
               撤销     → 一次性全部恢复
```

批量记录保存每个任务的完整副本和原始索引；撤销时按原索引升序恢复，保证
被删任务之间的相对顺序不变。撤销条显示「已删除 N 条」，单条时仍显示任务名。
若删除后用户又新增/排序，绝对索引允许因列表变化而偏移，但不能恢复重复 ID，
也不能只恢复其中一条。

**不做多级撤销栈。** 用户真正会用的就是「我刚才删错了」这一种；
栈会带来「撤销到第几步了」的界面负担。这个取舍之前已经定过一次
（单个模型时），批量沿用同一个。

### C4【开放·本次决定】工具条进入选择模式

采用「列表工具条 → 选择模式」，不采用另外两种：

| 方案 | 决定 | 原因 |
|---|---|---|
| 复选框常驻 | 不选 | 默认态每行多一个强视觉元素，列表密度下降；用户只是浏览时没有收益 |
| 长按进入 | 不选 | 桌面端没有长按提示，鼠标和键盘用户很难发现；也和双击编辑冲突 |
| 工具条进入 | **选用** | 入口可见、点击目标稳定，批量状态和单条编辑状态分离 |

在当前筛选/搜索行右侧增加「选择」按钮。进入后：

```text
顶部工具条：已选 N 条 · 全选当前结果 · 完成 · 删除 · 退出
每行左侧：仅在选择模式显示复选框；点击行/复选框切换该 ID
键盘：Ctrl+A 选中当前结果，Esc 退出，Delete 等同「删除」并先确认
```

交互不变量：

- 「全选当前结果」只作用于当前筛选和搜索后的可见 ID，不悄悄操作被过滤的任务；
  已全选时按钮变为「取消全选」。
- 「完成」只把选中且未完成的任务标为完成；完成项不重复计数，操作后清空选择
  并退出选择模式。
- 「删除」必须弹出带数量的确认框；确认后整批删除并显示可撤销条，取消不改变
  选择和数据。
- 退出路径至少有工具条「退出」、`Esc`、完成/删除后的自动退出；点击筛选、
  搜索或模型重建时清理不存在的 ID，不能把选择态卡死。
- 选择集合按任务 ID 保存，不按 delegate 行号保存；AI 新增任务或模型重排不能
  改变已经选中的任务。

**已知约束**：`TasksPage.qml` 现在**没有任何多选代码**（`selected` /
`multiSelect` / `checkedIds` 全是 0 处命中），所以是从零加，不是改。

## 五、阶段 D：设置分层

### D1【钉死】`advanced_mode` 的准入用**规则**，不用逐个拍脑袋

现在只门控 2 处。扩展时必须有可复述的判据，否则会变成「谁顺手谁加」。
注意：`default_settings()` 的 45 个键里包含迁移标记和运行参数，不能把
「有键」误算成「设置页必须有一个控件」。

规则：

> 一个设置项进 `advanced_mode`，当且仅当它**同时**满足：
> 1. 泛用户不需要改（默认值对大多数人是合适的）
> 2. **改错的代价 > 用不上的代价**
>
> 典型的第 2 条：需要外部前置条件（API Key、MCP 服务器、知识库文件），
> 或者改了之后在界面上看不出效果。

这条规则只判断「功能设置」；`advanced_mode` 是分层本身的控制，不参与归类，
必须常驻。迁移标记和运行时缓存也不属于设置项，不渲染控件。

反例（**不该**进门控）：`pet_scale`、`notify_enabled`、主题预设——
泛用户会想改，而且改错了当场看得见。

### D2【开放·本次决定】按规则给 45 个设置项分类

先说明边界：主题预设/颜色继续放在 `theme.json`，不是 `settings` 的 45 个键。
45 个键按下面四类处理；「内部」不是删掉，而是继续由迁移/运行逻辑维护，
不在设置页渲染控件。`advanced_mode` 本身是唯一例外：它是分层开关，
必须始终可见，不能把用户锁在高级设置之外。

```text
基础（23，默认可见）
focus_minutes, short_break_minutes, long_break_minutes,
rounds_before_long_break, auto_start_next, sound_enabled, notify_enabled,
pet_scale, pet_opacity, ui_scale, always_on_top, fade_when_idle, autostart,
sit_reminder_minutes, sit_reminder_enabled, afk_minutes, daily_goal_minutes,
quiet_when_fullscreen, ai_level, pet_click_action, pet_style,
pet_snap_enabled, update_check

高级（14，advanced_mode 开启后可见）
hotkey_dashboard, hotkey_focus, hotkey_task, hotkey_ask,
command_bar_anchor, pet_snap_distance, pet_edge_pose,
ai_max_steps, ai_memory_enabled, ai_auto_screenshot, ai_show_cursor,
ai_mcp_enabled, ai_openai_model, ai_openai_base

分层控制（1，始终可见）
advanced_mode

内部（7，不渲染设置控件）
move_step, clock_format, pet_snap_hide_ratio, onboarding_done,
update_last_check, update_last_check_ok, update_skipped_version
```

分类理由：四个全局热键和指令栏位置需要用户理解快捷键语法，写错后通常要
重启才能发现；贴边距离/姿势是调好即忘的细节；AI 步数、记忆、截图、MCP 和
服务商参数要有外部前置条件，改错的代价高于暂时看不到它们。相反，缩放、
宠物大小、通知、专注时长和 AI 权限是第一次使用就可能要调的，留在基础层。

实现上不要把整个模型配置卡藏进高级模式：未配置 AI 时，API Key 入口仍然
必须可见。自定义十六进制颜色也放到「主题预设」下的高级编辑区，但预设选择
和恢复当前预设按钮保持基础可见。

### D3【钉死】分层要有量化验收

```
测量条件：908×590 设置页、advanced_mode = false、未展开颜色编辑、
无更新可用、默认数据副本。
改动前实际可见控件：29 个
  PawSwitch 7 + PawSlider 4 + PawField 4 + PawButton 14
最低验收：改动后 ≤ 21 个（相对下降 ≥ 25%）
目标值：≤ 20 个；若低于目标，不能通过移除基础入口来换数字。
```

理由同 B3：没有视觉回归设施，只能靠数字。而且这个数字能防止
「加了门控但其实只藏了一个开关」这种自我安慰式的改动。

测试必须实际加载 `SettingsPage.qml`，按 `QQuickItem.isVisible()` 统计四类
控件；不能用 grep 统计 `visible:` 行，也不能把父卡片隐藏但子控件仍占位的
情况误判为通过。另加反向断言：基础入口（缩放、主题预设、宠物大小、通知、
AI 未配置时的模型设置）仍有可见、可交互控件。

## 六、阶段 E：紧凑模式 —— **暂缓，不是不能做**

### E0【修正】先说清这一段的结论到底是什么

**这一节我改过一次标题和结论。**（原稿写的是「本轮不做」，读起来像
「这件事做不了」，那是错的。）

准确的表述是：

> **E 阶段不是「无法修改」，而是「不能安全地一次性修改」。**

区别是实质性的：

| 说法 | 含义 | 对不对 |
|---|---|---|
| 「紧凑模式做不了」 | 永远不做 | ❌ 错。技术上完全可行 |
| 「本轮不做」 | 含糊 —— 是搁置还是放弃？ | ⚠️ 表述不清，容易被读成前者 |
| **「不能安全地一次性做」** | **需要先还基础设施的债，分步做** | ✅ 准确 |

所以这一阶段的定位是**下一阶段的基础设施工作**，不是「排除项」。
配套的三步路径见 E2。

### E1【钉死】为什么不能一次性做 —— 四条理由，都有数字

#### 理由一：`ui_scale` 耦合了字号和间距，不能复用

`Theme.px(v) = round(v * scale)`，而 `scale` 来自 `backend.uiScale` ——
**间距和字号共用同一个系数**。它是「整体缩放」（给看不清的人用的），
不是「紧凑」（给想一屏看更多的人用的）。

紧凑要的是**间距降、字号不变**，所以必须是独立轴，不能借 `ui_scale`。

#### 理由二：间距的 token 化率比看上去更差

实测（27 个 QML，去掉注释行）：

| 类别 | 写死 | 走 Theme | token 化率 |
|---|---|---|---|
| **`spacing`** | **169** | **11** | **6.1%** |
| `anchors.margins` | 83 | 10 | 10.8% |
| `Layout.*Margin` | 0 | 46 | **100%** |
| `Layout.preferred/minimum` 尺寸 | 41 | 7 | 14.6% |
| `width` / `height` 写死 | 29 | 0 | 0% |
| 合计 | **322** | **74** | 18.7% |

**这张表比原稿的「token 65 / 写死 201」更有用，因为它指出了钱在哪：**

- `Layout.*Margin` 已经 **100% 做完**（46 处）—— 有人做过一轮，别重复劳动
- **`spacing` 才是真正的大头：169 处写死，只有 11 处走 token**
- `anchors.margins` 次之（83 处）

现在加一个 `density`，只有 6.1% 的间距会跟着变 ——
结果就是**「有的地方紧、有的地方不紧」**，比不做更糟。

> 原稿那个「65 / 201」是把 `spacing` 和 `Margin` 合并数的，
> 数量级没错（比例约 1/4），但**掩盖了「哪一类已经做完、哪一类没动」**。
> 迁移的标的是 `spacing` 和 `anchors.margins`，不是 `Layout.*Margin`。

#### 理由三：尺寸是**推导**出来的，改间距会链式重算

| 指标 | 数量 |
|---|---|
| `Layout` 容器（Column/Row/Grid/Stack） | 175 |
| `implicitHeight` | **104** |
| 固定 `height: <数字>` | 36 |

**`implicitHeight` 比手写 `spacing` 的一半还多**，说明大部分尺寸是
**内容自撑**推导出来的。推导链越长，局部改间距越容易在某处塌掉 ——
表现就是按钮挤压、文本换行、滚动区域异常。

这 104 处不是「迁移成本」，是**风险来源**：它们不需要改，
但会在间距变化时重新计算，而**没有任何测试盯着算得对不对**。

#### 理由四：59/59 的逻辑回归保证不了视觉

回归是逻辑测试（数据、行为、断言）。它抓得住「函数返回错了」，
抓不住「这个卡片现在挤成一团」。

**没有视觉回归设施**，所以紧凑模式的正确性无法自动验证 ——
这决定了它必须**小步做**，每步都能人工看。

### E2【钉死】三步路径（这一步是 Codex 提的，比原稿好）

原稿把 E 当成一件事，只给了「先 token 化」再「加全局开关」两步。
**Codex 在中间插了一步「局部紧凑」，这个补充是对的**，采纳：

```
E1  间距 token 化（纯基础设施，不动视觉）
      ↓
E2  局部紧凑：只支持 AI 页 + 待办页
      ↓
E3  全局开关：comfortable / compact
```

**为什么 E2 这一步是必要的（而不是直接从 E1 跳到 E3）：**

- **缩小承诺范围**。只做两个页面，就不必承诺「全工作台都紧凑」——
  那是个大得多的承诺，而且每多一个页面就多一处可能塌掉的推导链。
- **提前拿到真实反馈**。AI 页信息密度提升最明显（实测 2025px 塞在
  330px 视口里），待办页次之。这两个页面验证过了，才知道 `density`
  的取值合不合适。
- **失败可退**。局部紧凑出问题只影响两个页面，不用回滚整个功能。

**E1 的验收：棘轮测试**（原稿已有，保留）

```
断言：写死的 spacing 数量 ≤ 上一次记录的值
      目标：单调下降，直到 0
```

棘轮而不是一次性全改的理由：169 处分散在约 20 个文件，
一次性改的风险是布局悄悄坏掉，而**我们没有视觉回归设施**能抓住它。
棘轮让这笔债可以分批还，且不会倒退。

**E1 迁移的优先级**（按实测数量排，不是按主观感受）：

| 文件 | 手写 spacing | 固定高度 | 备注 |
|---|---|---|---|
| `page/SettingsPage.qml` | 23 | 4 | |
| `page/AiPage.qml` | 25 | 0 | E2 的目标页面 |
| `AiSettingsPanel.qml` | 21 | 0 | E2 的目标页面 |
| `page/RemindersPage.qml` | 17 | 1 | |
| `page/TasksPage.qml` | 12 | 1 | E2 的目标页面 |
| `Dashboard.qml` | 7 | 10 | 固定高度最多 |

**先迁 E2 要用的那三个页面**（`AiPage` / `AiSettingsPanel` /
`TasksPage`），这样 E1 做完就能直接接 E2，不用等全部迁完。

### E3【钉死】现阶段**不显示**紧凑模式开关

即使 E1 做完，**也不要先加设置项**。

理由：用户看到一个「紧凑模式」开关就会去点，而那时候只有部分页面
变紧 —— 他看到的不是「紧凑模式」，是「界面变得不一致了」。
**一个半成品的开关比没有开关更伤信任**（这个项目已经有过一次：
`rose` 那个改了没用的死选项）。

所以顺序是：**先把页面做紧凑，最后才暴露开关**，而不是反过来。

### E4【开放】`density` 的取值与 E2 的范围

- `density` 具体取几档、系数是多少 —— 需要 E2 阶段实际看效果定

## 八、验证协议（对协作双方的约束）

这一节是**流程要求**，不是建议。本项目在这些点上已经栽过跟头。

### V1 每个阶段必须有断言，且登记进 `tools/regress.py` 的 `SUITES`

`SUITES` 是**唯一清单**，`build.py` 从它导入。**没登记的测试永远跑不到** ——
写多少都等于没写。（曾经打包前自测的清单比实际回归少 9 个套件，
于是 QML 语法错误能打进包里发出去。）

本方案的测试落点固定为：

```text
A：扩展 tools/themetest.py（已有登记）
B：扩展 tools/aipreview.py（已有登记）
C：新增 tools/taskbulktest.py，并显式登记进 SUITES
D：扩展 tools/advancedtest.py（已有登记）
```

因此当前基线是 58 个套件；实现 C 后预期是 59 个套件，不能在交付时仍写
「58 个」而漏报清单变化。

### V2 断言必须**被证明能抓住目标 bug**

写完断言之后，**故意把产品代码改坏**，确认断言变红；还原。

本项目栽过两次，两次都是「断言看起来在测，其实什么都没测」：

- 贴边朝向的断言读的是**测试自己写的常量**，把产品里的符号改反它照样全绿
- 上传工具第一版断言取错了键，在比较 `"" == ""`

> **一条从不失败的断言比没有断言更糟** —— 它给的是虚假的安心。

本轮至少做四个反向证明：

```text
A：把 Theme.qml 的一个 pick("...") 键拼错，themetest 必须红；
   把 readableOn 改回固定白字，气泡/按钮对比度断言必须红。
B：临时让一个折叠正文仍占原高度，或把未配置状态的设置卡隐藏，aipreview 必须红。
C：让批量删除循环调用 remove()，检查保存次数为 1 的断言必须红；
   让 undo 只恢复首项，批量撤销断言必须红。
D：把一个基础控件错误地绑到 advanced_mode，真实可见控件数量/反向入口断言必须红。
```

### V3 涉及「改用户数据」的改动，必须在**真实数据副本**上验证

`store.py` 那次规范化改动的做法可以照搬：复制真实
`pet_data.json`（576KB / 14 个顶层字段）→ 读 → 写 → 再读 → **逐字节比对**。
外加幂等性检查（第二次读写不能产生新变化）。批量任务操作的文件会有预期
业务变化，因此要比对「未选中任务、stats 之外的字段逐字节不变」；不能把
「文件成功写出」冒充成完整验证。`theme.json` 同理，预期只允许
`preset` 和 `colors` 发生差异，并验证旧格式升级后再次保存是幂等的。

「加载不报错」不算验证。

### V4 QML 颜色只能用 `#rrggbb` / `#aarrggbb` / `Qt.rgba()`

**不能**用 CSS 的 `"rgba(108,86,64,0.35)"`。QML 的 `color` 不接受它。
踩过一次，直接炸掉 5 个套件。预设有大量色值，这条尤其要注意。
`Theme.readableOn()` 返回的也是 `#rrggbb`；半透明装饰必须使用
`Qt.rgba()`，不能把 CSS 写法塞进预设表。

### V5 断言读产品实际值，不写字面量

反例：`check("角度是 -90", angle == -90)` 里的 `-90` 如果同时也是
测试自己传进去的参数，那它测的是自己的算术。

正例（上传工具那次）：`commits_to_publish` 的结果和本地 `git rev-list`
的输出比 —— 两边来自不同路径，对不上就是真有问题。

对比度测试从 `theme.PRESETS` / `theme.resolved()` 和运行后的 QML 属性读取
实际值；不要在测试里复制 A3 表格再和复制品比较。批量 ID 测试从真实
`Store.tasks` 读取，QML 可见控件测试从 `QQuickItem.isVisible()` 读取。

### V6 每阶段结束跑全量回归

`.venv\Scripts\python.exe tools\regress.py --quiet`

当前基线：**58 个套件全绿**。任何阶段完成后必须仍然全绿。

## 附录：对比度怎么算（A2b 用）

WCAG 2.x 的相对亮度和对比度。**不要用「看着差不多」代替计算** ——
「深色模式下这块发灰」这种判断，肉眼看不出是 2.9 还是 3.1。

```python
def srgb_to_linear(channel: float) -> float:
    """sRGB 分量（0~1）→ 线性光。注意是分段函数，不是简单的 2.2 次方。"""
    if channel <= 0.04045:
        return channel / 12.92
    return ((channel + 0.055) / 1.055) ** 2.4


def luminance(hex_color: str) -> float:
    """#rgb / #rrggbb / #aarrggbb 都收（#aarrggbb 是 QML 的写法，要跳过前两位）。"""
    text = hex_color.lstrip("#")
    if len(text) == 3:
        text = "".join(char * 2 for char in text)
    if len(text) == 8:                      # aarrggbb
        text = text[2:]
    red = srgb_to_linear(int(text[0:2], 16) / 255.0)
    green = srgb_to_linear(int(text[2:4], 16) / 255.0)
    blue = srgb_to_linear(int(text[4:6], 16) / 255.0)
    # 系数是按人眼感光灵敏度来的：绿最亮，蓝最暗
    return 0.2126 * red + 0.7152 * green + 0.0722 * blue


def contrast(foreground: str, background: str) -> float:
    first, second = luminance(foreground), luminance(background)
    lighter, darker = max(first, second), min(first, second)
    return (lighter + 0.05) / (darker + 0.05)
```

参考值（正文 4.5:1、大字 3:1 是 WCAG AA）：

| 谁 | 门槛 |
|---|---|
| 正文（`fsBody` 及以上） | 4.5:1 |
| 大字（约 ≥ 18px 或粗体 ≥ 14px） | 3:1 |
| 次要/最弱文字（本项目定为装饰性信息） | 3.0:1 |
| 图形元素（图标、开关圆点、边框） | 3:1 |

**这套配色是粉彩风格，白色画在任何粉彩上都到不了 4.5:1** ——
所以 A2c 那个问题（用户消息气泡）不是计算错了，是配色风格本身的取舍。
新预设如果也想走粉彩，就要接受「粉彩底上用深色文字」这个前提。

## 附：这份文档自己的修正记录

写方案的过程中**有四处判断被推翻**，记下来给 Codex 参考 ——
**不要相信文档里没标数据的结论**：

| 我一开始写的 | 实测结果 | 怎么改的 |
|---|---|---|
| 对比度门槛 4.5:1 | **默认主题自己过不了**（`textFaint` on `surfaceHi` = 2.89:1） | `textFaint` 微调到 `#978092`，新预设按棘轮 + 3.0 下限验收 |
| 「白字 on accent/violet/mint/gold 都不达标」→ 我改成「白字只有 2 处」 | **字面量确实只有 2 处，但 `PawButton._fg` 动态返回白字**（`primary` / `accent` / `danger` 三档）。所以这一处我**改了两次、第二次仍然错** | 加 `Theme.readableOn()` 共享前景规则，不只修气泡。见下 |
| 「AI 面板可以做折叠」 | `AiHistoryPanel` 已有 `expanded`，但语义是**整卡显隐** | B1 里写清三种语义的区别，避免被当成重复建设 |
| **「紧凑模式本轮不做」** | Codex 指出：这句话读起来像「做不了」，实际是「不能一次性安全做完」 | 第六节重写为三步路径（E1 → E2 → E3），补入「局部紧凑」这一步 |

### 第三条要单独展开讲：**验证方法决定了你能得出什么结论**

那一处我犯了两次错，方向相反：

1. **第一次（错）**：按「按钮上应该有白字」**假设**出四行不达标，
   写成了既有缺陷。这是**把假设当事实**。
2. **第二次（还是错）**：我用「搜 `#FFFFFF` / `white` 字面量」去验证，
   数出 2 处，于是**推翻了第一次的结论**，还在文档里写了
   「假设出来的问题不该写成既有缺陷」。

第二次错得更隐蔽：**字面量搜索只能否证关于字面量的论断**，
而我要否证的是**渲染出来的颜色**。`PawButton._fg` 是个 `switch`
表达式，实际返回 `"#ffffff"`，但搜索搜不到 —— 它不是字面量出现，
是计算结果。

于是：

- 我的**原始担心是对的**（accent 2.38:1、violet 2.74:1、rose 3.29:1）
- 我的**「纠正」是错的**，而且因为它带着「我做了验证」的权威感，
  比第一次的错更危险
- **Codex 找到了真正的答案**：字面量 2 处 + 动态 3 处

教训不是「要验证」（我验了），而是：

> **验证手段的覆盖范围，决定了它能支持什么结论。**
> 用「搜字符串」去核对「计算出来的值」，得到的"没有"是假阴性。

这和 V2 那条是同一件事的两面：V2 说「一条从不失败的断言比没有断言更糟」，
这里是「一个覆盖不到目标的验证比没有验证更糟」—— 因为它会**主动**
把一个正确结论推翻掉。

### 第四条和前面三条成因不同

前三条是**判断错了**（把假设当事实、方法覆盖不到）；第四条是
**措辞把「暂缓」写成了「放弃」**。

技术上没错，但传达错了，代价一样大 —— 下一个人读到「本轮不做」
会以为这件事不用再想。**写结论时要问一句「这句话会被读成什么意思」。**
