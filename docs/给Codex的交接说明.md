## 三、明确请你决定的三件事

### 1. 主题预设的色值与数量（文档 A3）

五条需求里用户提的是「浅色、深色、护眼、紧凑」。紧凑模式我建议本轮不做
（理由在文档 E0/E1，间距只有 24.4% 走 token，现在做会「又紧又不紧」）。

**色值我不定**，那是审美。我只有一个硬约束：

```
新预设不许比现状更差 —— 文字类另加绝对下限 3.0:1
（WCAG 对比度，公式在文档附录）
```

**注意**：我第一版写的是「正文 ≥ 4.5:1」，但算了一遍发现
**默认主题自己就过不了**（`textFaint` on `surfaceHi` = 2.89:1）。
拿产品当前达不到的标准要求新预设是挖坑，所以改成棘轮。
具体数字见文档 A2b。

### 2. 待办批量编辑的交互形式（文档 C4）

复选框常驻 / 长按进选择模式 / 工具条切换 —— **产品判断，你定**。

我只要求两条：

- 「全选」「批量完成」「批量删除」三个动作可达
- 退出选择模式的路径明确（不能进了出不来）

**已知约束**：`TasksPage.qml` 现在**没有任何多选代码**
（`selected` / `multiSelect` / `checkedIds` 全是 0 处命中），是从零加。

### 3. 用户消息气泡的对比度要不要顺手修（文档 A2c）

`AiBubble.qml:90` —— 用户自己发的消息是**白字画在 `Theme.violet`
（#b48ae0）气泡上，对比度 2.74:1**（AA 要 4.5）。

助手气泡是深色文字配浅底（9~10:1）。所以**用户自己的话比小爪的回复更难读**。

根因：粉彩（pastel）主色和白色天生对比度低，标准解法是粉彩上用深色文字。

**我倾向本轮不修** —— 改它要动默认主色，属于产品改版不是加预设。
但如果你的预设体系本来就要重选一遍主色，一并处理可能更划算。

**波及面已核实：只有这一处。**（`PawSwitch.qml:36` 那处白字是滑块圆点，
图形元素不适用文字对比度，别算进来。）

## 四、给你的四个陷阱提醒

这些都是这个项目**已经踩过**的，写在文档第八节，这里再点一遍：

### V2：断言必须被证明能抓住目标 bug（最重要）

写完断言后，**故意把产品代码改坏，确认断言变红，再还原**。

本项目栽过**两次**，两次都是「断言看起来在测，其实什么都没测」：

- 贴边朝向的断言读的是**测试自己写的常量**，把产品里的符号改反
  它照样全绿
- 上传工具第一版断言取错了键，实际在比较 `"" == ""`

> **一条从不失败的断言比没有断言更糟** —— 它给的是虚假的安心。

### V4：QML 的 `color` 只接受 `#rrggbb` / `#aarrggbb` / `Qt.rgba()`

**不能**用 CSS 的 `"rgba(108,86,64,0.35)"`。这个项目因此炸掉过 5 个套件。

预设有大量色值，**尤其注意**。

### V1：新测试必须登记进 `tools/regress.py` 的 `SUITES`

那是**唯一清单**，`build.py` 从它导入。**没登记的测试永远跑不到。**

曾经打包前自测的清单比实际回归少 9 个套件，于是 QML 语法错误
能打进包里发出去。

### V3：改「用户数据」的代码要在真实数据副本上验证

参考 `store.py` 规范化那次的验证方式：复制真实 `pet_data.json`
（576KB / 14 个顶层字段）→ 读 → 写 → 再读 → **逐字节比对** +
幂等性检查。「加载不报错」不算验证。

## 五、这份方案里我错过的三次（所以别全信它）

三处都是**先有印象、后补验证**，然后被自己的测量推翻：

| 我一开始写的 | 实测结果 |
|---|---|
| 对比度门槛 4.5:1 | 默认主题自己过不了（2.89:1） |
| 「白字 on accent/violet/mint/gold 都不达标」 | 白字全项目**只有 2 处**，一处还是图形元素 |
| 「AI 面板没有折叠」 | `AiHistoryPanel` 已有 `expanded`，但语义是**整卡显隐** |

共同点：把**假设**当成了**既有缺陷**。

同类错误在这个项目上不是第一次。就在写这份方案之前，我把
「180ms < 500ms 所以双击会残留指令栏」当结论，写了很长一段推理 ——
实验证明 Qt 的 `TapHandler` 会延后发 `tapped`，那个推断不成立。

**所以：文档里凡是带数字的结论我都测过，凡是没测的都标了【开放】。
不要相信没标数据的论断。** 如果你发现哪条只有推理没有数据，
那就是我要么漏标了，要么那条本身就不该被当成结论。

## 七、验收方式

每完成一个阶段，交付五样：

1. 代码 + 断言（登记进 `SUITES`）
2. **断言的有效性证明**（V2：改坏 → 变红 → 还原）
3. 量化验收数字：
   - 阶段 A → 对比度（文档附录有公式）
   - 阶段 B → `Flickable.contentHeight`（目标 < 900px）
   - 阶段 D → 设置页可见控件数量（目标下降 ≥ 25%）
4. 全量回归结果（58 个套件必须仍然全绿）
5. 提交信息写清**为什么这么选**和**验证到什么程度**

第 5 条特别说明：这个项目历史里**写得最有用的是那些主动说明
「我没能验证什么」的提交**。

比如碰撞箱那次的提交里写了「真实 OS 级点击没能测，因为会话无焦点，
前台窗口是 Idle」—— 后来用户反馈那个症状其实是远程投屏造成的，
**正是因为写了这句，才没让人误以为「已经修好了」**。

不要为了显得完整而省略不确定性。
